# 3. Руководство администратора

Администратор сканера отвечает за пользователей и права, проекты и allowlist,
справочники уязвимостей, уведомления, узлы-сканеры, журнал аудита, резервные
копии и обновления. Сканирование администратор не запускает — это задача оператора
([Руководство оператора](04-operator-guide.md)).

Разделы администрирования в меню: «Справочники», «Сканеры», «Уведомления»,
«Журнал аудита», «Пользователи и роли». Проекты и allowlist — в разделе «Проекты».

## 1. Первый вход

1. Откройте `http://<сервер>:8080` и войдите логином и паролем из
   `SCANNER_API_BOOTSTRAP_ADMIN` / `SCANNER_API_BOOTSTRAP_PASSWORD`.
2. Заведите оператора (раздел 2) — администратор прогоны не запускает.
3. Создайте проект и allowlist (раздел 3).
4. Проверьте «Справочники» → «Готовность справочников» (раздел 4).

Первый администратор создаётся один раз, пока в БД нет пользователей. После
этого переменные `SCANNER_API_BOOTSTRAP_*` можно убрать из `.env`.

## 2. Пользователи и роли

### 2.1. Роли

| Роль | Назначение |
|---|---|
| `admin` | пользователи и роли, проекты, allowlist, учёт активов, справочники, узлы-сканеры, уведомления, профили соответствия, журнал аудита; просмотр результатов |
| `operator` | сетевой поиск, запуск и остановка прогонов, расписания, разбор находок (ложные срабатывания), отчёты |
| `auditor` | только просмотр результатов, выгрузка отчётов, журнал аудита |
| `host_credentials` | дополнительное право: учётные записи активов и проверки с входом на хосты (по учётной записи, аудит конфигураций, проверка учёток). Выдаётся вместе с `operator`, когда заказчик передал доступы |
| `cred_audit` | дополнительное право: наборы проверки и аудит учётных данных (подбор паролей по согласованному списку). Выдаётся вместе с `operator`, только если проверка паролей согласована в договоре |

Пользователю можно назначить несколько ролей. Дополнительные роли не входят ни
в одну базовую, в том числе в `admin`.

### 2.2. Права

| Право | admin | operator | auditor | Что открывает |
|---|:-:|:-:|:-:|---|
| `manage_users` | ✓ | | | «Пользователи и роли» |
| `manage_engagements` | ✓ | | | проекты, учёт активов, группы, справочники, уведомления, профили соответствия |
| `manage_allowlist` | ✓ | | | allowlist проекта |
| `manage_nodes` | ✓ | | | «Сканеры»: заведение узлов, их сети, токены, отключение и удаление |
| `view_engagements` | ✓ | ✓ | ✓ | проекты, allowlist, справочники, каналы и узлы-сканеры — просмотр |
| `run_scan` | | ✓ | | прогоны, расписания, сетевой поиск, пересчёт соответствия |
| `view_report` | ✓ | ✓ | ✓ | сводка, активы, находки, прогоны, отчёты |
| `triage_findings` | | ✓ | | отметка ложных срабатываний |
| `view_audit` | ✓ | | ✓ | журнал аудита и его выгрузка |
| `host_credentials` | | | | только с ролью `host_credentials` |
| `cred_audit` | | | | только с ролью `cred_audit` |

Права проверяются на сервере при каждом запросе; отказ — ответ 403 и запись
`access_denied` в журнале. Права прогона по расписанию проверяются заново при
каждом срабатывании: если у владельца расписания их больше нет, расписание
выключается.

### 2.3. Управление пользователями

«Пользователи и роли» → «Создать пользователя»: логин (латиница, цифры,
`_ . @ -`), отображаемое имя, пароль (не короче 12 символов), роли. У
существующего пользователя можно сменить имя, пароль и роли или
заблокировать его. Удаления нет — блокируйте, чтобы сохранить авторство
записей журнала. Последнего активного администратора заблокировать или лишить
роли `admin` нельзя.

**Рекомендуемый минимум:** один `admin`, операторы по числу исполнителей,
`auditor` для того, кто принимает отчёты. Не совмещайте `admin` и `operator`
у одной учётной записи — это снимает разделение обязанностей.

**Вход.** Токен действует 60 минут (`SCANNER_API_TOKEN_TTL_MINUTES`). После 5
неудачных попыток подряд вход для логина блокируется на 15 минут
(`SCANNER_API_LOGIN_MAX_FAILURES`, `SCANNER_API_LOGIN_LOCKOUT_MINUTES`).

### 2.4. Вход через AD и двухфакторный вход

Оба способа **по желанию заказчика** и по умолчанию выключены; включаются
независимо друг от друга переменными в `.env` (подробно, с примерами —
[INSTALL.md, раздел 8а](../INSTALL.md#8а-вход-через-ad-и-двухфакторный-вход-по-желанию)).
Локальный вход работает всегда.

**Active Directory / LDAP** (`SCANNER_API_LDAP_URL` и др.). Пользователь
входит логином и паролем домена (`ivanov`, `CORP\ivanov` или
`ivanov@corp.local`); пароль проверяет контроллер, «Сканер» его не хранит.
Роли назначаются по группам AD (`SCANNER_API_LDAP_GROUP_ROLES`,
«DN группы`=>`роли») и пересчитываются при каждом входе; без подходящей группы
входа нет. В «Пользователях и ролях» такие учётки помечены «Домен»: пароль и
роли у них не редактируются, но учётку можно отключить. Локальный
пользователь с тем же именем важнее доменного. Только LDAPS или STARTTLS;
ошибка в настройках останавливает запуск `app`. Проверка настроек:
`scanner auth ldap-check [--username ivanov]`.

**Двухфакторный вход** (`SCANNER_API_MFA`): `off` — выключен, `optional` —
каждый включает себе в «Безопасности входа» (значок щита внизу меню),
`required` — обязателен всем, кто не в `SCANNER_API_MFA_EXEMPT_USERS`
(сервисные учётки интеграций). Код — из приложения-аутентификатора (Яндекс
Ключ, Google Authenticator и т. п.), при включении выдаются 10 одноразовых
кодов восстановления. Потерял телефон и коды — «Изменить» → «Сбросить 2FA».
Секреты 2FA зашифрованы ключом `SCANNER_CREDENTIALS_KEY`; при его смене 2FA
придётся настроить заново. Нужны верные часы на сервере (NTP).

Все входы, создание доменных пользователей, смена их ролей, включение,
отключение и сброс 2FA записываются в журнал аудита.

## 3. Проекты и allowlist

### 3.1. Проект

«Проекты» → «Новый проект»: название, заказчик, номер договора. Номер и
заказчик выводятся на обложке отчёта. Проект с прогонами удалить нельзя —
история работ по договору сохраняется.

### 3.2. Allowlist

Откройте проект → поле allowlist. Принимаются:

| Запись | Пример |
|---|---|
| адрес | `192.0.2.10` |
| подсеть CIDR | `192.0.2.0/28` |
| диапазон | `192.0.2.30-192.0.2.40` или кратко `192.0.2.30 - 40` |
| несколько записей | через запятую или с новой строки |

В примечании укажите основание: пункт договора, письмо заказчика. Вносите
только адреса из договора или приложения к нему. Кнопка «Из активов…»
добавляет в allowlist выбранные хосты из «Активов» (подряд идущие адреса
сворачиваются в диапазон).

Что гарантирует allowlist: цель вне него отбрасывается до запуска любого
движка, отказ пишется в журнал (`scan_request`, `deny`). Изменения allowlist
действуют на все будущие прогоны, в том числе по расписанию; уже идущий прогон
проверяет цели при постановке. Один прогон — не больше 4096 адресов.

### 3.3. Учёт активов

Вкладка «Активы» — все хосты проекта: найденные прогонами и сетевым поиском
заводятся автоматически, остальные — кнопкой «Добавить актив». Администратор
задаёт учётные атрибуты:

| Атрибут | На что влияет |
|---|---|
| Критичность (низкая / средняя / высокая / критическая; по умолчанию средняя) | балл приоритета находок хоста (×0,8 … ×1,3) |
| Владелец | маршрутизация уведомлений |
| Группы (например, «ДМЗ») | отчёт по группе, фильтры, маршрутизация уведомлений, разбивка соответствия |
| Теги | фильтры и поиск |

Атрибуты можно менять массово: отметьте хосты → панель «+ в группу», «+ теги»,
критичность. Корзина у хоста, найденного прогоном, сбрасывает атрибуты; у
заведённого вручную — удаляет его. Оператор и аудитор видят атрибуты только
для чтения.

### 3.4. Профили соответствия

«Соответствие нормативам» → профиль проекта (право `manage_engagements`):

1. Выберите профиль: ФСТЭК №117 (ГИС, класс К1–К3), №21 (ИСПДн, УЗ1–УЗ4),
   №239 (КИИ, категория 1–3), CIS Controls v8 (IG1–IG3), CIS Benchmark.
2. Задайте уровень (класс, УЗ, категорию, IG).
3. Исключите меры, которых нет в адаптированном наборе системы (например,
   виртуализация, беспроводной доступ, если их нет).
4. Отметьте «в отчёт», если раздел нужен в отчёте по умолчанию.

Процент считается автоматически в конце каждого прогона. После обновления
сканера, изменившего профили, оператор пересчитывает старые прогоны кнопкой
«Пересчитать». Перед первым отчётом заказчику набор мер №21/№239 и
сопоставление мер с проверками должен сверить методолог.

## 4. Справочники

### 4.1. Источники

| Источник | Что даёт | Автообновление по умолчанию (когда включено) |
|---|---|---|
| БДУ ФСТЭК | идентификаторы `BDU:…`, связь с CVE, наличие эксплойта, меры устранения | еженедельно, пн 04:00 |
| NVD (CVE) | CVSS, описания, CPE; после первой загрузки — только изменённые CVE | ежедневно 03:00 |
| Шаблоны Nuclei | сетевые проверки | ежедневно 05:00 |
| EPSS | вероятность эксплуатации (приоритет) | ежедневно 02:00 |
| CISA KEV | эксплуатируемые уязвимости (приоритет) | ежедневно 02:30 |
| Обновления Microsoft (MSRC) | KB и CVE для проверки Windows | еженедельно, вт 04:30 |
| Бюллетени дистрибутивов | исправленные версии пакетов и ядра: Debian, Ubuntu, RHEL и совместимые, ALT, Astra Linux, РЕД ОС, Alpine | еженедельно, пн 04:30 |

Автообновление **выключено по умолчанию**: сканер не выходит в интернет без
решения администратора. Включается в «Справочниках» → ✎ у источника; там же
меняется время. «Обновить сейчас» запускает загрузку вне расписания. Каждая
загрузка пишется в журнал (`feed_sync`); при ошибке может уйти уведомление
«Справочник не обновился».

**Готовность справочников** показывает по каждому источнику, есть ли данные,
сколько записей и что сделать, если нет. Во время загрузки видны этап,
«загружено N из M», скорость и оставшееся время. Первая полная загрузка NVD
без ключа идёт несколько часов — задайте `NVD_API_KEY`, будет примерно в 10
раз быстрее.

### 4.2. БДУ ФСТЭК

Скачайте `vullist.xlsx` с bdu.fstec.ru и загрузите одним из способов:

- в «Справочниках» → «Загрузить файл БДУ» (до 128 МБ);
- положите в `./data/vullist.xlsx` и выполните
  `docker compose exec app scanner feeds sync-bdu --file /data/vullist.xlsx`;
- задайте `BDU_FSTEC_FEED_URL` (своё зеркало) и включите автообновление.

Повторная загрузка безопасна: записи обновляются без дублей. Рекомендуемая
периодичность — еженедельно.

### 4.3. Бюллетени дистрибутивов

Нужны для проверки по учётной записи: без них сканер сравнивает версии
апстрима и показывает уязвимости, уже закрытые бэкпортом, с пометкой «Нет
данных вендора».

- `ADVISORY_RELEASES` — выпуски, загружаемые по расписанию
  (`debian:bookworm,ubuntu:jammy,rhel:9,astra:1.7,redos:7.3,…`). Оставьте
  выпуски заказчика: файлы большие.
- Выпуски, встреченные на хостах, подгружаются прямо в прогоне
  (`ADVISORY_ON_DEMAND=auto`): из `./data/advisories` — всегда, из интернета —
  только если автообновление бюллетеней включено. Недостающие выпуски видны в
  «Готовности справочников» с кнопкой загрузки.

Имена файлов для ручной поставки и свои адреса источников —
[INSTALL.md, раздел 7](../INSTALL.md#7-справочники-бду-и-nvd).

### 4.4. Закрытый контур

| Справочник | Как поставить без интернета |
|---|---|
| Всё сразу | комплект данных в `./data/bundle/` → импорт при старте или `scanner bundle import` |
| БДУ | файл `vullist.xlsx` (раздел 4.2) |
| NVD | фиды NVD 2.0: `scanner feeds sync-nvd --file /data/nvdcve-2.0-2024.json.gz` |
| EPSS, KEV | файлы `EPSS_FEED_PATH`, `KEV_FEED_PATH` |
| MSRC | документы CVRF в `./data/msrc` (`SCANNER_MSRC_FEED_PATH=/data/msrc`) |
| Бюллетени ОС | файлы в `./data/advisories` (`debian.json`, `ubuntu-jammy.xml.bz2`, `rhel-9.xml.bz2`, `alt-p10.zip`, `astra-1.7.xml`, `redos.xml`, `alpine-3.19.json`) |

### 4.5. Комплект данных

Комплект `scanner-data-<дата>.tar` — снимок всех справочников из БД с
манифестом, контрольными суммами и `NOTICE.txt` об источниках. После импорта
каждый источник докачивает только изменения с даты комплекта.

```bash
# собрать на эталонном стенде (там, где есть доступ к bdu.fstec.ru и сайтам вендоров)
docker compose exec app scanner bundle export --out /data/bundle/scanner-data-$(date +%Y%m%d).tar
docker compose exec app scanner bundle info /data/bundle/scanner-data-20261103.tar
# загрузить вручную (автоимпорт при старте — из ./data/bundle, самый свежий)
docker compose exec app scanner bundle import /data/bundle/scanner-data-20261103.tar [--force]
```

Повторный импорт того же комплекта ничего не перезаписывает. Комплект также
собирает workflow `data-bundle` в GitHub Actions. Условия передачи БДУ ФСТЭК и
OVAL Astra/РЕД ОС третьим лицам не опубликованы: уточните их, прежде чем
передавать комплект заказчику. Подробно —
[INSTALL.md, раздел 4а](../INSTALL.md#4а-комплект-данных-уязвимостей).

## 5. Уведомления

«Уведомления» → «Новый канал». Каналы настраивает `manage_engagements`,
просматривают все с `view_engagements`. По умолчанию каналов нет.

| Канал | Что отправляет | Настройки |
|---|---|---|
| Почта (SMTP) | письмо со сводкой и ссылкой на отчёт | сервер, порт, STARTTLS или SSL (вход по паролю без шифрования запрещён), логин, пароль, «От кого», «Кому» |
| Telegram | сообщение бота | id чата или `@канал`, токен бота |
| Syslog (CEF) | событие в SIEM (RFC 5424, ArcSight CEF); новые критичные — по пакету на находку | сервер, порт, UDP/TCP, facility, имя приложения |
| Jira | задача на каждую новую критичную находку, без дублей | адрес, ключ проекта, тип задачи, логин + токен API или персональный токен, метки, лимит задач за событие |

**События:** «Прогон завершён», «Новые критичные находки» (новые и
вернувшиеся), «Справочник не обновился» (повтор той же ошибки — не чаще раза
в сутки). Jira принимает только «Новые критичные».

**Маршрутизация:** пороги опасности и приоритета, группы и владельцы активов,
проекты. Ложные срабатывания в уведомления не попадают.

**Доставка:** сразу после события; неудача повторяется через 1, 5, 15 и 60 минут.
Ошибки параметров (неверный пароль, чат не найден) не повторяются. Исходы —
в «Журнале доставки», неудачу можно повторить вручную. Кнопка «Проверить»
отправляет тестовое сообщение.

**Безопасность:** пароли и токены каналов шифруются `SCANNER_CREDENTIALS_KEY`
и не возвращаются API. В сообщения попадают хост, порт, название, CVE/БДУ,
уровень и приоритет — без доказательств. Syslog передаётся без шифрования —
только внутри контура. Telegram и Jira идут через `HTTPS_PROXY`, если он задан.

## 5а. Узлы-сканеры

«Сканеры» — узлы для сегментов, куда центральный сервер не дотягивается по
сети (филиалы, ДМЗ, АСУ ТП). Узел — тот же образ без веб-интерфейса и БД; он
сам выходит на центр по HTTPS, забирает прогоны, выполняет их на месте и
возвращает результат. Заводит и меняет узлы право `manage_nodes`
(администратор), видят — все с `view_engagements` или `run_scan`. Установка
узла и правило межсетевого экрана —
[INSTALL.md, раздел 13в](../INSTALL.md#13в-узлы-сканеры-в-изолированных-сегментах).

**Добавить узел:** название, тип «Сетевой», сети сегмента (подсети, диапазоны,
адреса), описание, разрешить ли передавать узлу учётные записи. После
сохранения окно показывает токен и готовый `.env.node`; токен виден один раз,
в центре хранится только его отпечаток.

**Карточка узла:** статус («На связи», «Нет связи» — нет запросов дольше
90 с, «Ещё не подключался», «Отключён»), последняя связь, хост и версия узла,
локальный allowlist, что узел делает сейчас и сколько прогонов ждут его в
очереди. Предупреждения: сети узла шире локального allowlist; на узле нет
nmap, Nuclei, OpenSCAP, Lynis или SNMP (соответствующие проверки там не
выполнятся).

| Действие | Что происходит |
|---|---|
| «Изменить» | название, описание, сети, учётные записи. Новые сети действуют со следующего задания |
| «Токен» | новый токен; старый перестаёт действовать сразу. Закреплённый сертификат mTLS сбрасывается и закрепится заново |
| «Отключить» / «Включить» | отключённый узел не принимается центром и не предлагается при запуске |
| Удалить | только без прогонов в очереди и в работе; прошлые прогоны остаются в истории |

**Три рубежа allowlist.** Узел получает только цели, которые входят и в
allowlist проекта, и в сети узла. На самом узле действует ещё и локальный
allowlist (`SCANNER_NODE_ALLOWLIST`), который задают на месте и который центр
изменить не может. Результат узла центр ещё раз сверяет с разрешёнными сетями
и отбрасывает лишнее (`node_result_filtered` в журнале). Отказы на всех
рубежах пишутся в журнал аудита как `deny`; действия узла — от имени
`node:<название>`.

**mTLS (по желанию).** Кроме токена можно требовать клиентский сертификат
узла: проверку делает HTTPS-прокси центра, API доверяет заголовкам прокси
(`SCANNER_NODE_MTLS_VERIFY_HEADER`, `SCANNER_NODE_MTLS_FINGERPRINT_HEADER`) и
закрепляет отпечаток сертификата за узлом при первом подключении. Пример —
`docs/examples/nginx-node-mtls.conf`.

## 6. Журнал аудита

«Журнал аудита» (роли `admin`, `auditor`): кто, когда, что сделал и с каким
результатом. Пишутся вход, изменения пользователей, проектов, allowlist,
активов, учёток и каналов, каждый прогон и каждый запуск движка (с полной
командой nmap/Nuclei), выгрузки отчётов, загрузки справочников, отказы.
Секреты в журнал не попадают. Перечень действий —
[Справочник, 5.7](05-reference.md#57-действия-журнала-аудита).

Журнал только дописывается: изменение и удаление записей запрещены на уровне
БД. Срок хранения не ограничен.

**Выгрузка:** задайте субъект, период («24 часа», «7 дней», «30 дней» или
«С/По») и действия → **CSV** (UTF-8 с BOM, открывается в Excel) или **JSON**
(с шапкой фильтра и автором выгрузки). Время — UTC, до 100 000 записей за раз.
Сама выгрузка пишется в журнал (`audit_export`). Через API:

```bash
curl -H "Authorization: Bearer $TOKEN" -OJ \
  "http://<сервер>:8080/api/audit/export?format=csv&action=scan_start&since=2026-10-01T00:00:00Z"
```

## 7. Резервное копирование и восстановление

```bash
scripts/backup.sh                        # в ./backups/ГГГГ-ММ-ДД_ЧЧММСС
scripts/backup.sh /mnt/backup/scanner    # в свой каталог
scripts/restore.sh backups/2026-11-02_023000 --yes
```

| Что в копии | Содержимое |
|---|---|
| `db.dump` | вся БД: пользователи, проекты, прогоны, находки, справочники, журнал |
| `data.tar.gz` | каталог `./data`: known_hosts SSH, сертификаты WinRM, файлы справочников |
| `manifest.txt`, `SHA256SUMS` | время, ревизия миграций, коммит, контрольные суммы |

Копия снимается без остановки сервиса; скрипт проверяет, что дамп читается.
Восстановление останавливает `app` и `web`, пересоздаёт БД, возвращает
`./data` (текущий сохраняется рядом) и запускает сервисы. Без `--yes` ничего
не меняется.

- В `.env` при восстановлении должны быть **те же** `SCANNER_CREDENTIALS_KEY`
  и `SCANNER_API_SECRET`, что и при создании копии.
- Ежедневная копия с хранением 14 последних:

```cron
30 2 * * * cd /opt/scanner && COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml scripts/backup.sh >> /var/log/scanner-backup.log 2>&1 && ls -1dt backups/*/ | tail -n +15 | xargs -r rm -rf
```

- Храните копии на другом сервере или носителе.

## 8. Обновление и мониторинг

### 8.1. Обновление

```bash
cd /opt/scanner
scripts/backup.sh
git pull
docker compose up -d --build      # пересборка образов, миграции применяются при старте app
docker compose ps                 # дождаться (healthy)
```

Используйте именно `up -d --build`, а не `restart`: веб-интерфейс и
зависимости собираются в образы. Новые переменные из `.env.example` перенесите
в свой `.env`; что изменилось — в [сведениях о выпусках](06-release-notes.md).

**Откат:** `git checkout <коммит из manifest.txt копии>`, `docker compose up -d
--build`, затем `scripts/restore.sh <копия> --yes`. Миграции вниз
автоматически не откатываются: `alembic downgrade` на рабочей базе отклоняется,
пока не задан `SCANNER_ALLOW_DOWNGRADE=1`.

Прогон, шедший во время перезапуска, получает статус «Прерван»; его повторяют
кнопкой «Повторить». Прогоны в очереди выполняются после старта сами.

### 8.2. Мониторинг

| Проверка | Значение |
|---|---|
| `GET /health` (API) | процесс отвечает |
| `GET /health/ready` (API; снаружи — `http://<сервер>:8080/api/health/ready`) | БД доступна, схема на последней миграции, фоновые потоки работают; иначе 503 и причина |
| `GET /healthz` (веб) | nginx отвечает |
| `docker compose ps` | `healthy` / `unhealthy` по тем же проверкам |
| `docker compose logs app` | логи API и движков; ротация 5 файлов по 20 МБ на контейнер |

Сервис `app` работает строго одним процессом: прогоны, расписания,
автообновление и уведомления — фоновые потоки в нём. Не запускайте несколько
копий `app` на одну базу.

## 9. Устранение неполадок

| Симптом | Причина и решение |
|---|---|
| `app` не стартует, `[preflight] ОШИБКА: …` | в `.env` пустой или шаблонный секрет; исправьте названную переменную, `docker compose up -d` |
| `миграции не применены за N попыток` | БД недоступна или `POSTGRES_PASSWORD` не совпадает с паролем, с которым создан том `pg_data`; верните прежний пароль |
| Не пускает администратора | администратор создаётся только при пустой БД; пароль короче 12 символов не принимается |
| После перезапуска «выкидывает» на вход | не задан `SCANNER_API_SECRET` — ключ генерируется заново |
| «Вход заблокирован» | 5 неудачных попыток — подождите 15 минут |
| Учётки активов «не расшифровываются» | сменился `SCANNER_CREDENTIALS_KEY` (или `SCANNER_API_SECRET`, если отдельный ключ не задан); верните прежний или заведите учётки заново |
| Находки без БДУ | БДУ не загружена (раздел 4.2) |
| Сетевая проверка ничего не находит, `no templates provided` | нет шаблонов Nuclei: `docker compose exec app nuclei -update-templates` (нужен github.com) |
| «Бэкпорты не учтены», «Нет данных вендора» | нет бюллетеней выпуска ОС хоста: загрузите в «Готовности справочников» или положите файл в `./data/advisories` |
| Windows: «нет данных MSRC» | загрузите справочник MSRC (`scanner feeds sync-msrc`) |
| Прогон отклонён: цели нет в allowlist | добавьте адрес в allowlist проекта (раздел 3.2) |
| `port is already allocated` | порт хоста занят: задайте `SCANNER_WEB_PORT` / `SCANNER_API_PORT` / `SCANNER_DB_PORT` |
| Ошибка сборки на шаге Nuclei | нет доступа к github.com при сборке |
| `/health/ready` — 503 | причина в JSON ответа: БД, миграции или остановленный фоновый поток |
| Узел «Ещё не подключался» / «Нет связи» | на узле `docker compose -f docker-compose.node.yml logs node` и `… run --rm node check`: адрес центра (`https://`), токен, CA, правило МЭ узел → центр TCP 443 ([INSTALL.md, 17](../INSTALL.md#17-если-что-то-пошло-не-так)) |
| В логе узла «центр отклонил токен узла» | токен перевыпущен или узел отключён: новый токен в `.env.node`, `up -d` |

Ошибки, видимые оператору во время прогона, — в
[Руководстве оператора, 4.5](04-operator-guide.md#45-если-прогон-не-дал-результата).

## 10. Рекомендации по безопасной эксплуатации

- Публикуйте наружу только веб, через HTTPS-прокси; API и БД слушают
  `127.0.0.1`.
- Задайте отдельный `SCANNER_CREDENTIALS_KEY`, `chmod 600 .env`, копию `.env`
  храните вне сервера.
- Выдавайте `host_credentials` и `cred_audit` адресно и снимайте после
  окончания работ по договору; учётки активов удаляйте вместе с ними.
- Для заказчиков с повышенными требованиями включите строгую проверку ключей:
  `SCANNER_SSH_STRICT_HOST_KEYS=1` (ключи хостов заранее в
  `/data/ssh_known_hosts`), `SCANNER_WINRM_STRICT_CERTS=1` или
  `SCANNER_WINRM_TLS=ca`.
- Используйте на целях отдельные сервисные учётки с минимальными правами:
  чтения достаточно для проверки пакетов; `sudo` нужен только аудиту
  конфигураций.
- Регулярно выгружайте журнал аудита и проверяйте записи `deny`,
  `access_denied`, `cred_audit_*`, `node_auth`, `node_result_filtered`.
- Узлам-сканерам задавайте сети ровно по сегменту, а на узле — такой же или
  более узкий `SCANNER_NODE_ALLOWLIST`. Учётные записи передавайте только
  узлам, которым это нужно. Утерянный или скомпрометированный токен узла
  перевыпустите сразу; с mTLS — ещё и отзовите сертификат на прокси.
- Проверяйте восстановление из копии хотя бы раз в квартал.
