# 4. Руководство оператора

Руководство для того, кто проводит сканирование и разбирает результаты
(роль `operator`), и для того, кто принимает отчёты (роль `auditor`: всё то же
только для чтения). Проект и allowlist заводит администратор
([Руководство администратора, 3](03-admin-guide.md#3-проекты-и-allowlist)).

## 1. Начало работы

### 1.1. Порядок работ

1. **Подготовить цели**: согласовать с заказчиком адрес сканера и окно работ,
   получить учётные записи (раздел 2).
2. **Сетевой поиск**: какие хосты живы и какие порты открыты (раздел 3).
3. **Прогон**: выбрать цели и профиль проверки, запустить, следить за ходом
   (раздел 4).
4. **Разбор**: «Сводка», «Что исправить», ложные срабатывания (разделы 5–6).
5. **Отчёт** заказчику (раздел 9).
6. После устранения — **повторный прогон** и отчёт со сравнением.

### 1.2. Интерфейс

В шапке — выбор **проекта** (все разделы показывают данные выбранного),
поле быстрого поиска (`Ctrl+K`, раздел 10) и плашка идущего прогона с
прогрессом. Внизу меню — переключатель светлой и тёмной темы и значок щита
«Безопасность входа»: там видно, локальная у вас учётка или доменная, и,
если администратор разрешил, включается двухфакторный вход (код из
приложения на телефоне после пароля).

| Раздел меню | Назначение |
|---|---|
| Сводка | итог последнего прогона, что исправить первым, динамика, лента прогона |
| Проекты | allowlist, учётные записи активов, наборы проверки паролей |
| Активы | все хосты проекта с ОС, сервисами, уязвимостями и учётными атрибутами |
| Находки | план устранения «Что исправить» и таблица «Все находки» |
| Сетевой поиск | проверка доступности хостов и открытых портов без прогона |
| Сканирование | запуск прогонов, список и карточки прогонов |
| Расписание | регулярные прогоны |
| Соответствие нормативам | процент соответствия ФСТЭК и CIS по прогонам |
| Отчёты | выгрузка отчётов по завершённым прогонам |

Списки постраничные; фильтры, поиск, сортировка и страница хранятся в адресе —
ссылку можно переслать коллеге.

## 2. Подготовка целей

### 2.1. Что нужно на стороне заказчика

| Проверка | Требования к цели |
|---|---|
| Сетевая (обнаружение, Nuclei) | маршрут от сервера сканера; межсетевой экран и IDS пропускают адрес сканера |
| Linux по учётной записи | вход по SSH (пароль или ключ Ed25519/ECDSA/RSA); обычного пользователя достаточно — выполняются только команды чтения, без `sudo` |
| Аудит конфигураций Linux | то же + права root через `sudo` (для входа по ключу — `NOPASSWD`), включённая подсистема `sftp`; для OpenSCAP — пакет `openscap-scanner` (без него — только Lynis) |
| Аудит паролей | SSH; согласование проверки паролей в договоре; согласованный список пар «логин:пароль» |
| Windows по учётной записи | WinRM по HTTPS (5986); локальная или доменная учётка с правом чтения; вход только по паролю |
| Сетевое оборудование | SSH (22) с учёткой только на просмотр, которой доступна выгрузка конфигурации: Cisco IOS — `parser view` или privilege с `show running-config`; NX-OS — роль `network-operator`; Junos — класс `read-only`; MikroTik — группа `read`; Huawei — уровень с `display current-configuration`. Или SNMP v3 (authPriv, только чтение) / v2c RO — тогда только версия |

На хостах ничего не устанавливается. Аудит конфигураций копирует контент
проверки во временный каталог `/tmp/scanner-cfg.*` (права 0700) и удаляет его
после проверки, в том числе при ошибке.

### 2.2. Учётные записи активов

Нужно право `host_credentials`. Проект → «Учётные записи активов» →
«Добавить»:

| Поле | Значение |
|---|---|
| Способ входа | SSH, WinRM, «Сетевое устройство» (CLI по SSH), SNMP или СУБД (PostgreSQL / MySQL / MS SQL / Oracle) |
| Логин, порт | порт по умолчанию 22 (SSH, сетевое устройство), 5986 (WinRM), 161 (SNMP), 5432 / 3306 / 1433 / 1521 (СУБД); для WinRM — домен |
| База (СУБД) | база для входа: PostgreSQL — `postgres`, MS SQL — `master`; для Oracle — имя сервиса (обязательно) |
| Секрет | пароль; для SSH и сетевого устройства — или закрытый ключ (файлом, с парольной фразой); SNMP v2c — community; SNMP v3 — ключ аутентификации и ключ шифрования (не короче 8 символов); СУБД — только пароль |
| Платформа (сетевое устройство) | «Определить автоматически» или Cisco IOS / IOS XE / NX-OS / ASA, Juniper Junos, MikroTik RouterOS, Huawei VRP, Eltex ESR / MES |
| SNMP v3 | алгоритм аутентификации (SHA, SHA-256/512, MD5) и шифрования (AES-128/192/256, вариант Cisco, DES, без шифрования) |
| Повышение прав (SSH) | `sudo` (по умолчанию) или `none` — для входа сразу под root; для сетевых устройств и СУБД не применяется |
| Область действия | адреса и подсети из allowlist, к которым подходит учётка; пусто — все цели прогона |

На каждый хост пробуются подходящие учётки, начиная с самой узкой области, —
не больше трёх на протокол. Секреты хранятся зашифрованными и нигде не
показываются. Ключ SSH-хоста и сертификат WinRM запоминаются при первом
входе; если они изменятся, вход не выполняется (находка «Ключ SSH хоста не
прошёл проверку» / «Сертификат WinRM не прошёл проверку»).

**Проверка учёток без прогона.** «Активы» → значок ключа у хоста (или
«Проверить учётки…» для выбранных / всех) → «Проверить вход». Выполняется
одна попытка входа и сразу выход, команды на хосте не запускаются.

| Итог | Значит |
|---|---|
| Вход выполнен | учётка подходит |
| Отказ в доступе | неверный логин, пароль или ключ |
| Таймаут / Недоступен | порт не ответил или закрыт |
| Ключ хоста изменился | ключ SSH или сертификат WinRM отличается от запомненного |
| Нет учётки | ни одна учётка не покрывает адрес хоста |
| Частично | из нескольких учёток хоста подошли не все |

**Учётные записи СУБД.** Для аудита СУБД (модуль «Аудит СУБД», профиль
«Проверка СУБД») заведите у заказчика отдельную учётку СУБД **только на
чтение** и выдайте ей минимальные права. Без части прав аудит выполняется,
но зависящие правила получают «не проверено» — в сводке аудита перечислено,
какого права не хватило.

| СУБД | Учётка и права |
|---|---|
| PostgreSQL, Postgres Pro | `CREATE ROLE scan_ro LOGIN PASSWORD '…'; GRANT pg_read_all_settings TO scan_ro;` для проверки `pg_hba.conf` дополнительно `GRANT SELECT ON pg_hba_file_rules TO scan_ro; GRANT EXECUTE ON FUNCTION pg_hba_file_rules() TO scan_ro;` |
| MySQL, MariaDB | `CREATE USER 'scan_ro'@'<IP сканера>' IDENTIFIED BY '…';` для проверки учётных записей `GRANT SELECT (user, host, plugin, authentication_string) ON mysql.user TO 'scan_ro'@'<IP сканера>';` (MariaDB 10.4+: `GRANT SELECT ON mysql.user …` — это представление) |
| MS SQL Server | SQL-логин; `GRANT VIEW SERVER STATE TO [scan_ro]; GRANT VIEW ANY DEFINITION TO [scan_ro];` (SQL Server 2022: `VIEW SERVER SECURITY STATE`) |
| Oracle Database | `CREATE USER scan_ro IDENTIFIED BY "…"; GRANT CREATE SESSION, SELECT_CATALOG_ROLE TO scan_ro;` проверка паролей по умолчанию требует `SELECT ON dba_users_with_defpwd` |

Сканер выполняет только фиксированные запросы `SELECT`/`SHOW` к системным
представлениям, переводит сессию в режим «только чтение» (PostgreSQL,
MySQL/MariaDB, Oracle) и не читает прикладные данные и хэши паролей (для
MySQL проверяется только, пуст ли хэш). Пароль передаётся драйверу и в
журналы не попадает. TLS используется, если сервер его поддерживает
(PostgreSQL, MySQL/MariaDB, MS SQL); Oracle — обычный TCP (пароль по
протоколу O5LOGON не передаётся открытым текстом).

### 2.3. Наборы проверки паролей

Нужно право `cred_audit`. Проект → «Наборы проверки учёток» → «Добавить»: имя,
сервис `ssh`, строки `логин:пароль` (пустой пароль — `логин:`), до 200 записей.
Встроенных словарей нет: без набора аудит паролей ничего не проверяет.

## 3. Сетевой поиск

«Сетевой поиск» отвечает на вопрос «какие хосты в сети и какие порты
открыты» за минуты, без запуска прогона:

1. Адреса: введите или нажмите чип записи allowlist.
2. Порты: «1000 популярных», «Все 65 535» или свой список (`22, 80,
   8000-8100`); при необходимости — исключения.
3. По желанию: «Без проверки ping (-Pn)», «Определять сервисы (-sV)».
4. «Проверить». Ход виден полосой «Проверено N из M адресов»; «Остановить»
   прерывает проверку, готовые пачки сохраняются.

Живые хосты сразу попадают в «Активы». Ограничения: 2 одновременные проверки и
6 запусков в минуту на пользователя, до 1024 адресов в проверке. Адреса вне
allowlist отбрасываются.

## 4. Сканирование

### 4.1. Запуск прогона

«Сканирование» → «Запустить прогон»:

1. **Цели** — адреса, подсети CIDR и диапазоны (имена хостов не
   принимаются). Под полем — кнопки записей allowlist и «Выбрать хосты из
   активов…» с фильтрами по группе, ОС, тегу и критичности.
2. **Что проверить** — готовый профиль проверки:

   | Профиль | Модули | Нужна учётка |
   |---|---|---|
   | Полная проверка Linux | обнаружение, сетевая проверка, пакеты и ядро по SSH, аудит конфигурации, парольная политика | SSH |
   | Полная проверка Windows | обнаружение, сетевая проверка, обновления и ПО по WinRM | WinRM |
   | Сетевое оборудование | обнаружение, версия ОС устройства → CVE/БДУ, аудит конфигурации | сетевое устройство (SSH) или SNMP |
   | Только сетевая проверка | обнаружение, Nuclei и версии из баннеров | нет |
   | Только обнаружение | хосты, порты, сервисы, ОС | нет |

   Состав можно настроить вручную: движок поиска уязвимостей (Nuclei / По
   учётной записи / Оба / Не искать) и модули.
3. **Учётные записи** — для проверок с входом на хосты; **набор проверки** —
   для аудита паролей.
4. **Профиль нагрузки** (раздел 4.2). Для сетей заказчика начинайте с
   «Медленного».
5. **Где выполнять** — «Центральный сервер» или узел-сканер в сегменте
   (раздел 4.6). Список показывает статус узла и его сети.
6. **Название** — по желанию; пусто — по составу и целям, например
   `Обнаружение + Nuclei · 10.0.0.0/24`.
7. Отметьте подтверждение, что цели входят в объём работ по договору, и
   нажмите «Запустить».

Перед запуском форма показывает **итоговый состав прогона** и плашку «Полная
проверка» или «Неполная проверка» с причинами (например, нет учётки нужного
протокола). Аудит конфигураций автоматически добавляет проверку пакетов по
той же учётке и парольную политику. Цели вне allowlist отбрасываются, отказ
виден в ответе и в журнале. Если хост не отвечает на ping, включите
«Сканировать хосты, не отвечающие на ping (-Pn)» — прогон станет дольше.

### 4.2. Профили нагрузки

| Профиль | Запросов/с | Параллельно | Попыток входа на цель (аудит паролей) |
|---|---|---|---|
| Медленный (`gentle`) | 5 | 8 | 3 |
| Обычный (`normal`) | 20 | 32 | 5 |
| Быстрый (`aggressive`) | 100 | 128 | 8 |

Ориентир по времени: обнаружение (1000 портов) — около 5 минут на хост;
сетевая проверка одного веб-сервиса — 10–15 минут в «Обычном», около часа в
«Медленном». Время растёт с числом сервисов.

### 4.3. Ход прогона

| Статус | Значит | Можно повторить |
|---|---|---|
| В очереди | ждёт свободного исполнителя (одновременно идут 2 прогона) или, для прогона на узле, пока узел его заберёт («Ждёт узел …») | |
| Выполняется | идёт; видны этап, «K из M хостов», процент и «Осталось ≈ N мин» | |
| Завершён | все запланированные проверки выполнены | |
| Частично | часть проверок не выполнена или сломалась (SSH не ответил, нет учётки, пустой или недоступный справочник, ошибка Nuclei/nmap); результаты сохранены | ✓ |
| Ошибка | прогон не дал результата, причина в карточке | ✓ |
| Остановлен | остановлен кнопкой «Остановить» | ✓ |
| Прерван | служба сканера перезапускалась во время прогона или узел-сканер пропал со связи; результатов нет | ✓ |

Карточка прогона показывает:

- **ход выполнения** — этап, полосу прогресса, оценку оставшегося времени
  (уточняется по прошлым прогонам проекта);
- **ленту прогона** — начало и итог, модули, новые и вернувшиеся уязвимости
  по хостам, «не проверен»;
- **полноту проверки** — по каждому хосту и модулю: «Выполнено»,
  «Неприменимо», «Пропущено», «Хост недоступен», «Нет учётки», «Таймаут»,
  «Ошибка» — с причиной. Непроверенное не выдаётся за «уязвимостей нет» и не
  считается устранённым.

«Повторить» создаёт новый прогон с теми же целями, модулями, профилем и
учётками; права и allowlist проверяются заново.

### 4.4. Расписание

«Расписание» → «Новое расписание»: та же форма, что у прогона, плюс
периодичность:

| Вид | Когда |
|---|---|
| Каждый день | в указанное время |
| По дням недели | в выбранные дни |
| Раз в месяц | в указанное число; если его нет в месяце — в последний день |
| Один раз | в указанные дату и время, затем расписание выключается |

Время — в часовом поясе браузера, переходы на летнее время учитываются.
Прогон запускается с правами того, кто последним сохранил расписание; если
права отозваны, расписание выключается с пометкой «у владельца нет прав».
Пока предыдущий прогон расписания идёт, очередной пропускается. После простоя
сканера пропущенный запуск выполняется один раз. «Сейчас» ставит прогон
немедленно, не сдвигая график. Если в расписании выбран узел-сканер, каждый
запуск уходит на этот узел.

### 4.5. Если прогон не дал результата

| Что видно | Причина и действие |
|---|---|
| Прогон не создаётся: «ни одна цель не входит в allowlist» | адреса нет в allowlist проекта — обратитесь к администратору |
| «Ошибка»: хост недоступен, проверка не выполнена | хост выключен или не отвечает на ping — включите `-Pn` или проверьте маршрут |
| «Nuclei не загрузил ни одного шаблона», статус «Частично» или «Ошибка» | не скачаны шаблоны Nuclei — обратитесь к администратору |
| «справочник БДУ ФСТЭК пуст», статус «Частично» | БДУ не загружена: версии ПО и пакеты не с чем сопоставить. Загрузите БДУ в «Справочниках» и повторите прогон |
| «сопоставление … с БДУ/NVD не выполнено» | справочник был недоступен во время прогона (база перегружена, обрыв соединения) — повторите прогон |
| «Nuclei исключил хост из проверки после серии ошибок соединения» | хост перестал отвечать посреди проверки — проверьте его доступность, повторите с профилем ниже |
| «nmap прервал сканирование хоста по host-timeout» | порты хоста найдены не все — повторите прогон с меньшим числом целей или более медленным профилем |
| Проверка паролей: «остановлено: блокировка входа» / «ошибок соединения подряд» | проверены не все учётные данные из набора; это не «слабых паролей нет» |
| «Вход по учётной записи отклонён» | неверный логин, пароль или ключ; проверьте учётку из «Активов» (раздел 2.2) |
| «Таймаут SSH: пакеты не проверены», статус «Частично» | SSH не ответил; повторите прогон, проверьте фильтрацию порта |
| «Ключ SSH хоста не прошёл проверку» | ключ хоста сменился; если это ожидаемо (переустановка), администратор удаляет старую запись из `/data/ssh_known_hosts` |
| «sudo требует пароль» | для учётки с ключом нужен `NOPASSWD` в sudoers |
| «Бэкпорты не учтены» / «Нет данных вендора» | нет бюллетеней выпуска ОС — загрузите в «Справочниках» (нужно право администратора) |
| «Пакетов 0» | на хосте нет dpkg / rpm / apk |
| Windows: «обновления Windows не проверены», статус «Частично» | справочник MSRC не загружен или в нём нет версии ОС хоста — загрузите MSRC в «Справочниках» |
| Сетевая проверка прервана по таймауту | найденное сохранено; разделите цели или выберите профиль быстрее |
| Прогон на узле долго «В очереди» — «Ждёт узел …» | узел не на связи (статус в «Сканерах») — сообщите администратору; прогон дождётся узла |
| «Ни одна цель не прошла allowlist: договора и сетей узла в центре либо локальный allowlist узла» | цели вне сетей узла или вне его локального allowlist; выберите другой узел или «Центральный сервер», либо попросите администратора поправить сети узла |
| «Прогон прерван: узел-сканер перестал выходить на связь» | узел выключился или потерял связь посреди прогона; «Повторить», когда узел снова «На связи» |
| «узлу … запрещено передавать учётные записи» | в карточке узла запрещена передача учёток: уберите учётки или попросите администратора разрешить |
| «узел не поддерживает модули … обновите образ узла» | версия узла старше центра — администратор обновляет образ узла |

### 4.6. Прогон на узле-сканере

Узел-сканер — сканер, установленный внутри сегмента, куда центральный сервер
не дотягивается (филиал, ДМЗ, АСУ ТП). Узлы заводит администратор в разделе
«Сканеры»; там же видно, на связи ли узел и какие сети он проверяет.

- В форме прогона выберите узел в «Где выполнять». Узел получит только цели,
  которые входят и в allowlist проекта, и в сети узла; остальные отбрасываются
  с записью в журнал. На самом узле действует ещё и его локальный allowlist.
- Прогон стоит «В очереди» («Ждёт узел …»), пока узел его не заберёт, обычно
  несколько секунд. Если узел не на связи, прогон ждёт его, а не завершается
  ошибкой.
- Дальше всё как у обычного прогона: ход, лента, «Остановить» (узел узнаёт об
  остановке в течение ~10 с и не начинает следующие модули), находки, отчёты,
  сравнение, уведомления.
- В карточке прогона и в списке прогонов указано, где он выполнялся.

### 4.7. Прогон на автономном узле (закрытый сегмент)

Автономный узел ставится там, куда нельзя провести даже исходящее соединение до центра (АСУ ТП, закрытый контур). Его тоже выбирают в «Где выполнять», но центр такой прогон не выполняет и сам узлу ничего не передаёт: задание и результат переносятся файлами.

1. На странице прогона «Выгрузить задание» (срок действия — от 7 до 60 дней, по умолчанию 14). Скачается файл `.scnjob`; прогон перейдёт в «Выполняется».
2. Перенесите файл на узел и выполните там `scanner node run-job <файл> --out /media --confirm-authorized` (администратор узла).
3. Перенесите файл результата `.scnres` обратно и нажмите «Загрузить результат» на странице прогона или в «Сканерах». Дальше всё как у обычного прогона.

Файлы на носителе зашифрованы и подписаны: посторонний их не прочитает, а изменённый, чужой или повторный файл центр не примет. Потеряли файл задания — «Скачать задание ещё раз». Задание больше не нужно — «Отменить задание». Не загрузили результат за срок + 3 дня — прогон завершится ошибкой. Подробно — [offline-node.md](../offline-node.md).

## 5. Сводка

«Сводка» показывает последний прогон проекта:

- строка **«Главное»** — что исправить первым, сколько новых уязвимостей и
  сколько вернулось после исправления;
- **число открытых уязвимостей** и изменение к прошлому прогону, плитки по
  уровням опасности, доля сопоставленных с БДУ;
- **«Исправить в первую очередь»** — пять первых действий плана устранения;
- **график** открытых уязвимостей по уровням за «10 прогонов», «3 месяца» или
  «Год» (кнопка «Таблицей» — те же числа таблицей);
- **самые уязвимые хосты** и **лента прогона** (идущего или последнего).

Переключатель «Новый / Прежний» возвращает прежний вид сводки.

## 6. Находки

### 6.1. «Что исправить»

Вид по умолчанию: находки сгруппированы в **действия** администратора —
«Обновить пакеты … до …», «Обновить ядро Linux и перезагрузить», «Настроить:
…», «Сменить учётные данные: …», «Нет исправления: …». Вверху — «N действий
закрывают M находок на K хостах». Действия упорядочены по приоритету.

В карточке действия: ОС и выпуск, шаги с командами под ОС хоста
(`apt-get`, `yum`, `dnf`), команда проверки (`dpkg-query`, `rpm -q`,
`uname -r`), хосты с установленной версией, закрываемые CVE/БДУ и бюллетени.
Кнопка «Скопировать» копирует команды. Для пакетов без исправления у вендора
— компенсирующие меры из БДУ. Фильтры: опасность, вид действия, ОС, поиск по
пакету, бюллетеню или адресу.

### 6.2. «Все находки»

Таблица находок прогона с фильтрами по опасности, модулю, статусу, наличию БДУ
и поиском по CVE, БДУ, хосту, `хост:порт`. Режим «По хостам» группирует
строки. Карточка находки содержит:

| Поле | Что значит |
|---|---|
| Идентификаторы | `BDU:ГГГГ-NNNNN`, `CVE-…`, CVSS |
| Опасность | Критический, Высокий, Средний, Низкий, Информационный |
| Приоритет | ранг и балл с перечнем факторов (раздел 6.3) |
| Уверенность | «Подтверждено» (пакет на хосте, проверка Nuclei), «Вероятно», «Не подтверждено» (версия из баннера) |
| Источник | пакет на хосте, бюллетень вендора, сетевой баннер, проверка Nuclei, аудит конфигурации и т. д. |
| Доказательство | что именно обнаружено (версия пакета, ответ сервиса, правило) |
| Рекомендации и ссылки | как устранить; ссылки только на источники устранения: бюллетени вендора, БДУ, NVD, CWE |

Информационные находки (сводки модулей, причины «не проверено») приоритета
не получают; флажок «Ложные срабатывания» показывает отмеченные находки.

### 6.3. Приоритет

Приоритет отвечает на вопрос «что исправлять первым» и учитывает больше, чем
CVSS: наличие в каталоге CISA KEV, вероятность эксплуатации EPSS, отметку
эксплойта в БДУ и критичность актива. Ранг 1 — первым. Ярлыки: от 85 баллов —
критический, от 65 — высокий, от 40 — средний. Сроков устранения приоритет не
содержит. Формула — [Справочник, 5.6](05-reference.md#56-формула-приоритета).

### 6.4. Ложные срабатывания

Если находка не подтвердилась, откройте её карточку → «Отметить как ложное
срабатывание» и укажите обоснование (право `triage_findings`). Отметка:

- ставится на хост + порт + уязвимость + модуль и действует во всех будущих
  прогонах проекта;
- исключает находку из сводки, счётчиков, плана устранения, уведомлений и
  сравнения; в отчёте такие находки — отдельным последним разделом с
  обоснованием, автором и датой;
- снимается кнопкой «Снять отметку».

На странице хоста в виде «По ПО» можно отметить сразу все уязвимости одного ПО
— на этом хосте или на всех хостах прогона с этой версией.

### 6.5. Статусы находок при сравнении

| Статус | Значит |
|---|---|
| Новая (`new`) | появилась впервые |
| Открыта (`open`) | была и осталась |
| Устранена (`fixed`) | была в прошлом прогоне, сейчас нет (только если хост этим модулем проверен) |
| Регрессия (`regression`) | была устранена и появилась снова |

Находка сопоставляется между прогонами по хосту, порту, идентификатору
уязвимости и модулю.

## 7. Активы

«Активы» — все хосты проекта, даже ещё не проверявшиеся. По умолчанию для
каждого хоста показаны **последние данные**: по каждому виду проверки
берётся последний прогон, где хост действительно проверен. Если в новом
прогоне хост был недоступен, старые находки не считаются устранёнными.
Переключатель «Прогон» показывает данные одного прогона.

- Фильтры: группа, ОС (чипы семейств), критичность, тег, поиск; флажок «По ОС»
  делит таблицу на группы.
- ОС определяется по самому точному источнику: учётная запись
  (`/etc/os-release`) → баннеры сервисов → отпечаток стека nmap. Astra Linux и
  РЕД ОС надёжно различаются только по учётной записи.
- **Страница хоста**: ОС, порты и сервисы, установленные пакеты, уязвимости
  списком или «По ПО» (с сортировкой), ядро Linux отдельной строкой, ложные
  срабатывания, кнопки «Проверить доступность» и проверки учёток.

Критичность, владельца, теги и группы меняет администратор.

## 8. Соответствие нормативам

«Соответствие нормативам» показывает процент выполнения технических мер по
профилям проекта (ФСТЭК №117, №21, №239, CIS Controls v8, CIS Benchmark) для
выбранного прогона, с разбивкой по группам активов и хостам. Процент — доля
выполненных мер среди проверенных автоматически. Организационные меры
(«проверяется вручную») и меры, которые не удалось проверить («не
проверена»), в процент не входят.

Для осмысленного результата прогон должен включать аудит конфигураций с
учётной записью (для Windows — проверку по WinRM). После обновления сканера
оператор может пересчитать старый прогон кнопкой «Пересчитать».

## 9. Отчёты

«Отчёты» или меню отчёта в карточке прогона. Отчёт строится по завершённому
прогону (кроме «В очереди» и «Выполняется»).

| Параметр | Варианты |
|---|---|
| Формат | просмотр HTML в интерфейсе; выгрузка **PDF**, **Word (.docx)**, **HTML**, **JSON** |
| Версия | **Полный** — с рекомендациями и планом; **Краткий** — без плана, по находкам только ссылки на устранение |
| Сравнить с | без сравнения (по умолчанию) или более ранний завершённый прогон проекта — добавляет раздел сравнения и тренд |
| Группа | весь проект или одна группа активов — в отчёте только её хосты |
| Разделы | «План устранения», «Соответствие: <профиль>» — включаются и снимаются флажками |

**Структура полного отчёта:**

1. Обложка: заказчик, договор, прогон, дата.
2. Резюме для руководства: распределение по опасности, доля БДУ, ключевые
   выводы, полнота проверки.
3. Исправить в первую очередь: формула приоритета и топ-15.
4. План устранения (если включён).
5. Соответствие требованиям (если выбран профиль).
6. Сравнение с предыдущим прогоном (если выбран «Сравнить с»).
7. Результаты по хостам.
8. Детальные результаты для инженеров: каждая находка с подтверждением,
   рекомендацией и ссылками.
9. Ложные срабатывания (если есть).

Сроков устранения в отчёте нет; в JSON поле сохраняется для интеграций.
Каждая выгрузка пишется в журнал аудита (`export`).

Из командной строки:

```bash
docker compose exec app scanner report --run 12 --format pdf --out /app/report-12.pdf
docker compose exec app scanner report --run 12 --format docx --brief --out /app/report-12-brief.docx
docker compose exec app scanner report --run 12 --compare-to 9 --format pdf --out /app/report-12-vs-9.pdf
```

Файл появится в каталоге установки на сервере.

## 10. Быстрый поиск

`Ctrl+K` (на macOS `⌘K`) или поле в шапке ищет по выбранному проекту:

| Что набрать | Что найдётся |
|---|---|
| имя пакета (`openssl`) | действия плана, хосты с версией пакета, ПО, CVE/БДУ, команды |
| `CVE-…` или `BDU:…` | находки прогона с этой уязвимостью |
| адрес или имя хоста | хост, в том числе ещё не проверявшийся |
| `>` + текст (`>openssl`) | только команды; `Enter` копирует шаги действия |

`↑`/`↓` — выбор, `Enter` — открыть, `Esc` — закрыть.
