# 2. Руководство по установке

Руководство описывает требования, варианты развёртывания и порядок установки.
Полная пошаговая инструкция с учебным стендом и разбором каждой переменной —
[INSTALL.md](../INSTALL.md).

## 2.1. Требования к серверу

| Параметр | Минимум | Для сотен хостов и регулярных прогонов |
|---|---|---|
| ОС | Linux x86_64 (Debian 12, Ubuntu 22.04+ или аналог); arm64 — сборка с `--build-arg TARGETARCH=arm64` | то же |
| Процессор, память | 2 vCPU, 4 ГБ ОЗУ | 4 vCPU, 8 ГБ ОЗУ (оценка, не замер) |
| Диск | 20 ГБ (справочники в БД занимают несколько ГБ) | 50 ГБ и отдельный носитель для резервных копий (оценка) |
| ПО | Docker Engine 24+, Compose v2; для production — Compose v2.24.4+ | то же |
| Время | синхронизированные часы (NTP): расписания и журнал аудита опираются на время сервера | то же |

Сканер в простое занимает около 1 ГБ ОЗУ, во время прогона больше. Если на
сервере уже работают другие контейнеры, проверьте свободные порты, имена
проектов и подсети по [INSTALL.md, раздел 5.1](../INSTALL.md#51-если-на-машине-уже-работают-другие-контейнеры).

Узлу-сканеру в изолированном сегменте нужны Linux, Docker Engine 24+ и
Compose v2. PostgreSQL и веб-интерфейса на узле нет, справочники хранятся в
центре, поэтому ему хватает меньшего: 2 vCPU, 2 ГБ ОЗУ, 10 ГБ диска (оценка,
не замер).

## 2.2. Сетевые доступы

| Откуда → куда | Порт / адрес | Зачем | Обязательно |
|---|---|---|---|
| Рабочие места → сервер сканера | TCP 8080 (`SCANNER_WEB_PORT`) или 443 через HTTPS-прокси | веб-интерфейс и API (`/api`) | да |
| Сервер → цели из allowlist | ICMP, TCP-порты сканирования (по умолчанию 1000 популярных) | обнаружение, сетевая проверка | да |
| Сервер → цели | TCP 22 (или порт учётки) | проверка по учётной записи Linux, аудит конфигураций, аудит паролей | при работе с учётками |
| Сервер → цели | TCP 5986 (HTTPS); 5985 — только при `SCANNER_WINRM_ALLOW_HTTP=1` | проверка Windows по WinRM | при работе с Windows |
| Сервер → сетевые устройства | TCP 22 (CLI по SSH), UDP 161 (SNMP) | проверка сетевого оборудования | при работе с сетевым оборудованием |
| Сервер → интернет | `services.nvd.nist.gov`, `epss.cyentia.com`, `www.cisa.gov`, `api.msrc.microsoft.com`, `security-tracker.debian.org`, `security-metadata.canonical.com`, `security.access.redhat.com`, `rdb.altlinux.org`, `dl.astralinux.ru`, `redos.red-soft.ru`, `secdb.alpinelinux.org`, `github.com` (шаблоны Nuclei) | автообновление справочников | нет: в закрытом контуре — комплект данных |
| Сервер → интернет при сборке | Docker Hub, PyPI, npm, GitHub | сборка образов | только на машине сборки |
| Сервер → почта, Telegram, Jira, SIEM | адреса из настроек каналов | уведомления | по желанию |
| Узел-сканер → сервер (HTTPS-прокси) | TCP 443, только исходящее от узла | задания и результаты узла (`/api/node/v1/`) | при узлах-сканерах |
| Узел-сканер → цели своего сегмента | как у сервера в строках выше | проверка сегмента на месте | при узлах-сканерах |

Выгрузку БДУ ФСТЭК с `bdu.fstec.ru` обычно скачивают вручную и кладут файлом;
автоматическая загрузка возможна с зеркала (`BDU_FSTEC_FEED_URL`).

Контейнеру `app` выданы `NET_RAW` и `NET_ADMIN`: они нужны nmap для
SYN-сканирования и определения ОС. Маршрут до целей проверяется с сервера:
`ip route get <адрес цели>`. Межсетевые экраны и IDS на стороне заказчика
должны пропускать адрес сканера — согласуйте это до первого прогона.

Требования к самим объектам проверки (учётные записи, `sudo`, WinRM) — в
[Руководстве оператора, раздел 2](04-operator-guide.md#2-подготовка-целей).

## 2.3. Варианты развёртывания

| Вариант | Состав | Когда |
|---|---|---|
| Пилот / стенд | `docker-compose.yml` | ознакомление, приёмка, учебный стенд. Код `app` монтируется с хоста |
| Production | `docker-compose.yml` + `docker-compose.prod.yml` | рабочая установка: код только из образа, проверка секретов при старте, `restart: always` |
| Закрытый контур | production + комплект данных (+ образы, перенесённые `docker save`/`docker load`) | нет доступа в интернет |
| С узлами-сканерами | любой из вариантов выше + `docker-compose.node.yml` на машине в каждом изолированном сегменте | сегменты, куда сервер не дотягивается по сети: филиалы, ДМЗ, АСУ ТП. Из центра к узлу соединений нет; установка — [INSTALL.md, раздел 13в](../INSTALL.md#13в-узлы-сканеры-в-изолированных-сегментах) |

## 2.4. Установка

**1. Получить дистрибутив.**

```bash
git clone https://github.com/azuresong-afk/scanner-way.git /opt/scanner
cd /opt/scanner
```

**2. Задать параметры.** Скопируйте шаблон и замените все `CHANGE_ME`:

```bash
cp .env.example .env && chmod 600 .env
sed -i "s|^SCANNER_API_SECRET=.*|SCANNER_API_SECRET=$(openssl rand -base64 48 | tr -d '\n')|" .env
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$(openssl rand -hex 24)|" .env
sed -i "s|^SCANNER_CREDENTIALS_KEY=.*|SCANNER_CREDENTIALS_KEY=$(openssl rand -base64 48 | tr -d '\n')|" .env
# пароль первого администратора (не короче 12 символов) задайте вручную:
#   SCANNER_API_BOOTSTRAP_ADMIN, SCANNER_API_BOOTSTRAP_PASSWORD
grep CHANGE_ME .env      # не должно остаться ничего
```

| Обязательный параметр | Требование |
|---|---|
| `POSTGRES_PASSWORD` | стойкий пароль; после первого старта не меняется (хранится в томе `pg_data`) |
| `SCANNER_API_SECRET` | ключ подписи токенов, ≥ 32 символов |
| `SCANNER_CREDENTIALS_KEY` | ключ шифрования учётных записей и токенов каналов, ≥ 16 символов. **Храните копию вне сервера**: без него сохранённые учётки не расшифруются |
| `SCANNER_API_BOOTSTRAP_ADMIN`, `SCANNER_API_BOOTSTRAP_PASSWORD` | первый администратор; создаётся один раз, пока в БД нет пользователей |

Остальные параметры имеют рабочие значения по умолчанию — полный перечень в
[Справочнике, раздел 5.8](05-reference.md#58-параметры-окружения).

**3. Подложить данные об уязвимостях** (рекомендуется до первого старта):

- выгрузка БДУ ФСТЭК: `cp /путь/vullist.xlsx ./data/vullist.xlsx` — загрузится
  при первом старте (около 2 минут на ~98 600 записей);
- либо комплект данных `scanner-data-<дата>.tar` в `./data/bundle/` — в нём
  сразу БДУ, NVD, EPSS, KEV, MSRC, бюллетени ОС и шаблоны Nuclei
  ([INSTALL.md, раздел 4а](../INSTALL.md#4а-комплект-данных-уязвимостей)).

**4. Запустить.**

```bash
export COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml   # для production
docker compose up -d --build
docker compose logs -f app
```

Первая сборка занимает 5–15 минут. При старте `app` сам: проверяет секреты
(production) → применяет миграции схемы → импортирует комплект данных или
выгрузку БДУ → обновляет шаблоны Nuclei (если есть сеть) → запускает API.
Последняя строка успешного старта — `Uvicorn running on http://0.0.0.0:8000`.

**Закрытый контур.** Соберите образы на машине с интернетом и перенесите их:

```bash
docker compose build
docker save -o scanner-images.tar scanner-app scanner-web postgres:16
# на целевом сервере, в каталоге с тем же репозиторием и .env:
docker load -i scanner-images.tar
docker compose up -d --no-build
```

Имена образов — `<проект>-app` и `<проект>-web`, где проект Compose по
умолчанию — имя каталога (`/opt/scanner` → `scanner`); точные имена покажет
`docker compose images`. Справочники обновляйте новым
комплектом данных или файлами в `./data/advisories`, `./data/msrc`
([Руководство администратора, 4.4](03-admin-guide.md#44-закрытый-контур)).

## 2.5. Проверка установки

```bash
docker compose ps                                  # app, web, db — running (healthy)
curl -s http://127.0.0.1:8000/health               # {"status":"ok"}
curl -s http://127.0.0.1:8000/health/ready         # "status":"ok": БД, схема, фоновые потоки
curl -s http://127.0.0.1:8080/healthz              # ok
```

Откройте `http://<сервер>:8080` и войдите первым администратором. В
«Справочниках» → «Готовность справочников» убедитесь, что БДУ загружена.

Если `app` не стартует, причина — в `docker compose logs app`; типовые случаи
разобраны в [Руководстве администратора, раздел 9](03-admin-guide.md#9-устранение-неполадок).

## 2.6. Ввод в эксплуатацию

Перед первой работой с сетью заказчика:

- [ ] Перед веб-интерфейсом стоит HTTPS-прокси; в `.env` задан
      `SCANNER_API_PUBLIC_URL` (ссылки на отчёты в уведомлениях).
- [ ] Копия `.env` хранится вне сервера.
- [ ] Заведены пользователи: администратор, оператор, при необходимости
      аудитор; права `host_credentials` и `cred_audit` выданы только тем, кому
      они нужны по договору ([Руководство администратора, 2](03-admin-guide.md#2-пользователи-и-роли)).
- [ ] Загружены БДУ ФСТЭК и NVD; для проверок по учётной записи — бюллетени
      дистрибутивов заказчика; для Windows — MSRC.
- [ ] В «Справочниках» включено автообновление нужных источников (по
      умолчанию выключено) или определён порядок поставки комплектов данных.
- [ ] Для аудита конфигураций в образе есть контент SCAP Security Guide:
      `docker compose exec app ls /usr/share/xml/scap/ssg/content`.
- [ ] Создан проект, в allowlist внесены только адреса из договора.
- [ ] Ежедневная резервная копия поставлена в cron
      ([Руководство администратора, 7](03-admin-guide.md#7-резервное-копирование-и-восстановление)).
- [ ] Пройден чек-лист приёмки [TESTING.md](../TESTING.md) хотя бы в объёме
      шагов 1–8 и 10.

## 2.7. Удаление

```bash
cd /opt/scanner
scripts/backup.sh /mnt/backup/scanner     # если данные нужны
docker compose down -v                    # удаляет контейнеры и тома (БД, шаблоны Nuclei)
cd / && rm -rf /opt/scanner               # код, .env и ./data
```
