# 1. Общее описание

## 1.1. Назначение

Scanner — сетевой сканер уязвимостей для **авторизованного** анализа
защищённости по договору (pentest-by-contract) и регулярного контроля
уязвимостей в инфраструктуре заказчика. Продукт:

- находит хосты, открытые порты, сервисы и ОС;
- выявляет уязвимости ПО и сопоставляет их с **БДУ ФСТЭК России** и CVE/NVD;
- проверяет конфигурации по CIS Benchmarks и мерам ФСТЭК;
- по согласованию с заказчиком проверяет стойкость паролей;
- оценивает соответствие приказам ФСТЭК №117, №21, №239 и CIS;
- строит план устранения с командами для администраторов и отчёты для
  заказчика (HTML, PDF, Word, JSON);
- отслеживает динамику: новые, устранённые и вернувшиеся уязвимости.

Главный результат работы — понятный отчёт с привязкой каждой уязвимости к
идентификатору БДУ ФСТЭК и рекомендациями по устранению.

## 1.2. Возможности

| Область | Что делает | Как |
|---|---|---|
| Обнаружение и инвентаризация | живые хосты, порты, сервисы с версиями, ОС | nmap (`-sV`, `-O`) |
| Сетевой поиск | быстрая проверка доступности и портов без прогона | nmap только по портам |
| Сетевая проверка уязвимостей | уязвимости сервисов снаружи, без учётной записи | шаблоны Nuclei + сопоставление версий из баннеров |
| Проверка по учётной записи, Linux | пакеты и работающее ядро → CVE/БДУ с учётом бэкпортов вендора | SSH, только команды чтения; dpkg / rpm / apk; бюллетени дистрибутивов |
| Проверка по учётной записи, Windows | недостающие обновления и уязвимое ПО | WinRM (HTTPS + NTLM); справочник MSRC; реестр ПО |
| Сетевое оборудование | версия ОС устройства → CVE/БДУ; аудит конфигурации (Telnet/HTTP, SNMP, хранение паролей, AAA, ACL, журналы, NTP) | Cisco IOS/IOS XE/NX-OS/ASA, Juniper Junos, MikroTik RouterOS, Huawei VRP, Eltex ESR/MES; SSH только на просмотр или SNMP v2c/v3 |
| Аудит конфигураций | нарушения CIS Benchmark и требований ФСТЭК/ГОСТ (свой контент) | OpenSCAP + SCAP Security Guide, Lynis; по SSH с `sudo` |
| Парольная политика | блокировка после неудачных входов, длина, сложность, срок пароля | чтение PAM / `login.defs` / pwquality, без попыток входа |
| Аудит учётных данных | слабые и стандартные пароли SSH по согласованному набору | контролируемый модуль с жёсткими лимитами попыток |
| Приоритизация | «что исправлять первым»: ранг и балл по CVSS, CISA KEV, EPSS, эксплойту БДУ, критичности актива | прозрачная формула ([Справочник, 5.6](05-reference.md#56-формула-приоритета)) |
| План устранения | действия «обновить пакет / ядро / настроить / сменить пароль» с командами под ОС хоста | «Находки» → «Что исправить» |
| Соответствие нормативам | процент выполнения технических мер по профилю | ФСТЭК №117 (К1–К3), №21 (УЗ1–УЗ4), №239 (кат. 1–3), CIS Controls v8, CIS Benchmark |
| Учёт активов | критичность, владелец, теги, группы; последние известные данные по каждому хосту | вкладка «Активы» |
| Отчёты и динамика | полный и краткий отчёт, разрез по группе активов, сравнение с выбранным прогоном | HTML, PDF, DOCX, JSON |
| Регулярность | прогоны по расписанию, автообновление справочников | встроенные планировщики |
| Уведомления | итоги прогона, новые критичные находки, сбои справочников | почта, Telegram, syslog (CEF), Jira |
| Контроль действий | ролевая модель, журнал аудита только на дописывание, выгрузка CSV/JSON | RBAC, `audit_log` |

## 1.3. Архитектура

```
 Браузер ──HTTPS-прокси (рекомендуется)──► web (nginx, :8080)
                                              │  /api/* → app
                                              ▼
 ┌───────────────────────── app (API + движки, один процесс) ─────────────────────────┐
 │ REST API, RBAC, аудит                                                               │
 │ Оркестратор прогонов: allowlist-гейт → план модулей → rate limit → модули           │
 │ Модули: discovery · vuln · auth_inventory · win_inventory · netdev_audit ·          │
 │         config_audit · password_policy · cred_audit                                 │
 │ Фоновые планировщики: расписания прогонов, автообновление справочников,             │
 │                       повтор уведомлений, сторож прерванных прогонов                │
 │ Движки в образе: nmap, Nuclei, OpenSCAP, Lynis                                      │
 └───────────────┬──────────────────────────────────────────────┬──────────────────────┘
                 │                                              │ SSH / WinRM / SNMP / сеть
                 ▼                                              ▼
        db (PostgreSQL 16)                            цели из allowlist проекта
  прогоны, находки, активы, справочники
  (БДУ, NVD, EPSS, KEV, MSRC, бюллетени ОС),
  журнал аудита
```

Продукт поставляется как набор контейнеров Docker Compose:

| Сервис | Назначение | Доступ |
|---|---|---|
| `web` | веб-интерфейс (React), проксирует `/api/*` на `app` | порт 8080, единственный, открытый в сеть |
| `app` | API, оркестратор, модули и движки сканирования, планировщики | `127.0.0.1:8000` |
| `db` | PostgreSQL 16, данные в томе `pg_data` | `127.0.0.1:5432` |

Каталог `./data` на сервере хранит выгрузки справочников, комплект данных,
запомненные ключи SSH-хостов и сертификаты WinRM.

**Поток данных прогона.** Оператор выбирает проект, цели и профиль проверки →
каждая цель проверяется по allowlist (всё вне allowlist отбрасывается и
пишется в журнал) → модули выполняются по порядку с ограничением скорости →
результаты нормализуются в единую запись «находка» и сопоставляются с БДУ,
NVD и бюллетенями вендоров → после завершения считаются сравнение с прошлым
прогоном, приоритеты, соответствие нормативам и отправляются уведомления.

## 1.4. Модель безопасности

Сканер — инструмент двойного назначения, поэтому ограничения встроены в ядро,
а не в интерфейс:

| Механизм | Как работает |
|---|---|
| Allowlist проекта | цели вне allowlist отбрасываются до запуска движков; allowlist перечитывается при каждом запуске, в том числе по расписанию, и перед каждой пачкой сетевого поиска |
| Подтверждение объёма работ | без отметки «цели входят в объём работ по договору» (в CLI — `--confirm-authorized`) прогон не создаётся |
| Разделение обязанностей | администратор управляет пользователями и allowlist, но не сканирует; оператор сканирует, но не меняет allowlist |
| Отдельные права на чувствительные модули | вход на хосты по учётным записям — право `host_credentials`; проверка паролей — право `cred_audit`; оба выдаются только явно |
| Ограничение нагрузки | профили «Медленный / Обычный / Быстрый» задают скорость запросов и параллельность; лимит 4096 адресов на прогон |
| Защита секретов | пароли, ключи и токены хранятся зашифрованными (`SCANNER_CREDENTIALS_KEY`), не возвращаются API и не пишутся в журналы |
| Только чтение на целях | проверки по учётной записи выполняют команды чтения; аудит конфигураций работает во временном каталоге, который удаляется после проверки |
| Проверка подлинности целей | ключ SSH-хоста и сертификат WinRM запоминаются при первом входе (TOFU); при смене вход не выполняется |
| Журнал аудита | каждое действие пользователя и каждый запуск движка (с командой) записываются; журнал только дописывается на уровне БД |
| Защита входа | пароли не короче 12 символов; 5 неудачных входов подряд — блокировка на 15 минут; токен действует 60 минут |

## 1.5. Поддерживаемые платформы

**Сервер сканера:** Linux x86_64 (или arm64 со сборкой под `TARGETARCH=arm64`),
Docker Engine 24+, Compose v2.

**Объекты проверки:**

| Платформа | Без учётной записи | По учётной записи |
|---|---|---|
| Debian, Ubuntu | сеть, баннеры | пакеты и ядро по бюллетеням вендора; OpenSCAP + Lynis |
| RHEL, CentOS, Rocky, AlmaLinux, Oracle Linux, МСВСфера | сеть, баннеры | пакеты и ядро по OVAL Red Hat; OpenSCAP + Lynis (RHEL-совместимые, Fedora, SLES) |
| Astra Linux, РЕД ОС, Альт | сеть, баннеры (дистрибутив обычно не различим) | пакеты и ядро по OVAL вендора; конфигурации — Lynis |
| Alpine | сеть, баннеры | пакеты по secdb Alpine; конфигурации — Lynis |
| Windows | сеть, баннеры | недостающие KB по MSRC, ПО из реестра, параметры безопасности (WinRM) |
| Сетевое оборудование: Cisco, Juniper, MikroTik, Huawei, Eltex | сеть, Nuclei, баннеры | версия прошивки → CVE/БДУ, аудит конфигурации (SSH); только версия (SNMP) |
| Прочие узлы (СУБД, веб-приложения) | сеть, Nuclei, баннеры | не поддерживается |

**Источники данных об уязвимостях:** БДУ ФСТЭК (выгрузка `vullist.xlsx`),
NVD (CVE, CVSS, CPE), FIRST EPSS, CISA KEV, Microsoft MSRC, бюллетени
дистрибутивов (трекер Debian, OVAL Ubuntu, Red Hat, ALT, Astra Linux, РЕД ОС,
secdb Alpine), шаблоны Nuclei. Справочники загружаются из интернета по
расписанию или поставляются файлом — комплектом данных для закрытого контура.

## 1.6. Производительность

Ориентир — десятки и сотни хостов в прогоне. Замеры на PostgreSQL 16 без
настройки СУБД (подробно — [INSTALL.md, раздел 11](../INSTALL.md#11-находки-и-привязка-к-бду)):

| Операция | 100 тыс. находок | 1 млн находок |
|---|---|---|
| Страница находок с фильтром | 0,08 с | 0,3 с |
| Поиск подстроки (CVE, название) | 0,4 с | 3,4 с |
| Сводка прогона | 0,2 с | 0,7 с |

Время прогона определяется профилем нагрузки и числом сервисов: на один хост
с веб-сервисом сетевая проверка в профиле «Обычный» занимает 10–15 минут,
в «Медленном» — около часа. Одновременно выполняются 2 прогона
(`SCANNER_API_RUN_WORKERS`).

## 1.7. Термины и сокращения

| Термин | Значение |
|---|---|
| Проект (договор, engagement) | объект работ: заказчик, номер договора, allowlist, учётные записи, наборы проверки, активы, профили соответствия |
| Allowlist | перечень адресов, подсетей и диапазонов, которые разрешено сканировать по договору |
| Прогон (scan run) | один запуск сканирования по целям проекта с выбранными модулями |
| Модуль | часть прогона, выполняющая один вид проверки (`discovery`, `vuln`, …) |
| Движок поиска уязвимостей | Nuclei (снаружи), «По учётной записи» (изнутри) или оба |
| Профиль проверки | готовый набор модулей: «Полная проверка Linux», «Полная проверка Windows», «Сетевое оборудование», «Только сетевая проверка», «Только обнаружение» |
| Профиль нагрузки | ограничение скорости и параллельности: «Медленный», «Обычный», «Быстрый» |
| Учётная запись актива | логин и пароль/ключ для входа на хосты (SSH или WinRM) с областью действия; для сетевых устройств — SSH на просмотр или SNMP |
| Набор проверки | согласованный список пар «логин:пароль» для аудита учётных данных |
| Находка (finding) | результат проверки: уязвимость, нарушение конфигурации, слабый пароль или информационная запись |
| Актив | хост проекта с учётными атрибутами (критичность, владелец, теги, группы) |
| Полнота проверки (coverage) | что реально проверено по каждому хосту и модулю и почему что-то не проверено |
| Бэкпорт | исправление уязвимости, перенесённое вендором дистрибутива в старую версию пакета без смены версии апстрима |
| Ложное срабатывание | находка, отмеченная специалистом как неподтверждённая; исключается из подсчётов и отчётов |
| Регрессия | уязвимость, ранее устранённая и появившаяся снова |
| БДУ | Банк данных угроз безопасности информации ФСТЭК России, идентификатор `BDU:ГГГГ-NNNNN` |
| CVE / NVD | идентификатор уязвимости MITRE / национальная база уязвимостей США |
| CVSS | балльная оценка опасности уязвимости (0–10) |
| EPSS | оценка вероятности эксплуатации уязвимости (FIRST) |
| KEV | каталог эксплуатируемых уязвимостей CISA |
| MSRC | центр реагирования Microsoft, источник данных об обновлениях (KB) |
| OVAL | формат бюллетеней безопасности дистрибутивов |
| TOFU | доверие при первом использовании: ключ хоста запоминается при первом входе |

## 1.8. Ограничения

- Аудит учётных данных проверяет только SSH; парольная политика — только Linux
  (политики Windows и домена не проверяются).
- Проверка по учётной записи: Linux по SSH, Windows по WinRM (только пароль),
  сетевое оборудование по SSH (только команды просмотра) или SNMP (только
  версия, без аудита конфигурации). СУБД и глубокое сканирование
  веб-приложений (DAST) не поддерживаются.
- Сетевое оборудование: в БДУ версия часто указана на уровне ветки («15.0»),
  такие записи сопоставляются через CVE из NVD — без NVD часть БДУ может не
  найтись. Правила для Huawei и Eltex написаны по документации вендора.
  Неверный community SNMP v2c не отличить от недоступного агента.
- Для Astra Linux, РЕД ОС и Альт нет контента SCAP Security Guide: аудит
  конфигураций выполняет только Lynis. Требования ФСТЭК/ГОСТ можно проверять
  своим datastream.
- Без учётной записи дистрибутив Linux определяется по баннерам сервисов:
  Astra Linux и РЕД ОС обычно видны как «Linux» или Debian.
- Соответствие нормативам оценивает только технические меры на узлах;
  организационные меры помечаются «проверяется вручную». Состав мер профилей
  №21 и №239 и сопоставление мер с проверками перед первым отчётом заказчику
  должен сверить методолог.
- Один экземпляр сервиса `app` на базу (без кластеризации); распределённые
  сканеры не поддерживаются. Вход через Active Directory (LDAP) и
  двухфакторный вход (TOTP) — по желанию заказчика, по умолчанию выключены
  ([Руководство администратора, 2.4](03-admin-guide.md#24-вход-через-ad-и-двухфакторный-вход));
  единый вход (SSO) для нескольких продуктов — в составе «Платформы».
- Хранение старых прогонов не ограничено по сроку: политика очистки не
  реализована.

Перечень соответствует версии из [сведений о выпусках](06-release-notes.md);
снятые ограничения отмечаются там же.
