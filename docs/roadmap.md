# Дорожная карта и промты для параллельной разработки

Документ описывает, как довести сканер от каркаса (итерация 1, PR #1) до рабочего
продукта, разбив работу на **независимые задачи, которые можно вести в параллельных
тредах**. Каждая задача владеет своим набором файлов (папкой/модулем) и оформляется
**отдельным PR в `main`**, поэтому треды не конфликтуют между собой.

**Приоритет №1 (явно от заказчика):** научиться **сопоставлять находки с БДУ ФСТЭК**
(и с CVE/NVD). Это задача **T2**, самая детальная ниже.

**Сквозное требование (от заказчика):** итог — **понятный отчёт с рекомендациями по
устранению**. Рекомендации берутся из БДУ («Возможные меры по устранению»), из мер
NVD/вендора и из правил бенчмарка при аудите конфигураций. Это задача **T6**.

## 2. Граф зависимостей и волны параллелизации

```
                 [PR #1: фундамент — интерфейсы, схема, парсер БДУ]
                                   │  (смёржить в main)
        ┌───────────────┬──────────┴───────┬───────────────────┐
     ВОЛНА 1 (полностью параллельно, папки не пересекаются)
        │               │                  │                   │
      T1 core+БД     T2 БДУ/NVD +        T3 discovery        T6 reporting
     (persistence,   сопоставление       (nmap)              (HTML/PDF/DOCX/
      allowlist→БД)  ★ПРИОРИТЕТ★                               JSON + рекоменд.)
        │               │                  │                   │
        └──────┬────────┴─────────┬────────┴─────────┬─────────┘
            ВОЛНА 2 (зависят от интерфейсов волны 1; строятся на фикстурах)
               │                  │                  │
          T4 vuln (Nuclei,    T5 config audit    T7 API+RBAC+
          использует T2)      (OpenSCAP/Lynis    wiring оркестратора
                               по SSH)            (зависит от T1)
               │
            ВОЛНА 3
               │
          T8 cred audit (контролируемый) + сквозная интеграция +
          отчёт-тренд по всем модулям
```

**Принцип бесконфликтности:** каждый тред меняет только свои файлы (ниже в «Владеет»).
Общий `pyproject.toml` — только дописывание зависимостей в конец списка.
Каждый тред: ветка `feat/<area>`, свой PR в `main`, свои тесты, зелёный `docker build`.

**Оценка параллелизма:** волна 1 — 4 треда одновременно; волна 2 — 3; волна 3 — 1–2.

## 4. Промты для параллельных тредов

Каждый промт самодостаточен (тред стартует без контекста этого чата). Общий префикс
ниже добавляется к каждому.

### Общий префикс (вставляется в начало каждого промта)
> Контекст: репозиторий `azuresong-afk/scanner-way` — сетевой сканер уязвимостей для
> **авторизованного** security-тестирования по договору (pentest-by-contract). Все
> модули работают только по целям из allowlist, с rate limiting и аудитом действий;
> это встроено в ядро (`scanner/core/`). Язык — Python 3.12. Базовая ветка — `main`
> (после мёржа PR #1 там есть интерфейсы и схема). Работай в ветке `feat/<area>`,
> оформи **отдельный PR в `main`**, добавь тесты, не ломай `docker build`. Меняй
> только файлы из раздела «Владеет» — остальные модули делают другие треды
> параллельно. Уважай контракты `scanner/core/models.py` и `scanner/modules/base.py`,
> не меняя их без крайней необходимости (если меняешь — отметь в PR). Соблюдай
> безопасность: никаких действий вне allowlist, все внешние вызовы — через лимиты
> `RateProfile` и с записью в `ctx.audit`.

### ★ T2 — Сопоставление с БДУ ФСТЭК и NVD (ПРИОРИТЕТ №1)
> Задача: реализовать загрузку справочников уязвимостей и движок сопоставления
> находок с **БДУ ФСТЭК** и **CVE/NVD** — это важнейшая функция продукта.
>
> Владеешь: `scanner/feeds/nvd.py`, `scanner/feeds/matcher.py`,
> метод `sync()` в `scanner/feeds/bdu_fstec.py`, тесты в `tests/`.
>
> Что сделать:
> 1. **БДУ loader.** Парсер уже готов (`BduFstecFeed.iter_records()` разбирает
>    XLSX-выгрузку вида `vullist.xlsx`: лист «Уязвимости», `BDU:ГГГГ-NNNNN`,
>    извлечение CVE из колонки «Идентификаторы других систем», базовая оценка CVSS).
>    Реализуй `sync()`: upsert записей в таблицу `reference_bdu_entry` (поля см.
>    `db/migrations/0001_initial.sql`), включая `cve_ids[]`.
> 2. **NVD loader** (`feeds/nvd.py`): загрузка CVE из NVD (JSON feeds или API 2.0,
>    ключ в `NVD_API_KEY`) в `reference_nvd_cve` — CVSS, CPE, ссылки.
> 3. **Matcher** (`feeds/matcher.py`, `VulnMatcher.enrich(finding)`) — ядро задачи:
>    - если у находки есть CVE (`finding.vuln_id` или `cve_ids`) → подтянуть запись
>      NVD и **все связанные записи БДУ** (поиск по `reference_bdu_entry.cve_ids`
>      содержит данный CVE), заполнить `finding.bdu_ids`, `cve_ids`, `cvss`, severity;
>    - если CVE нет, но есть сервис+версия (`ServiceInfo`) → сопоставление по CPE:
>      сервис/продукт/версия → CPE → CVE из NVD → далее как выше; плюс по
>      вендору/названию/версии ПО напрямую искать в БДУ (поля `vendor`/`software`/
>      `versions`).
>    - приоритет идентификатора БДУ в выводе: находка должна нести И CVE, И `BDU:…`.
> 4. Направление severity: единая шкала (critical/high/medium/low/info) из CVSS и из
>    текстового уровня опасности БДУ.
>
> Критерии приёмки:
> - `sync()` БДУ грузит образец без ошибок; юнит-тест маппинга уже есть
>   (`tests/test_bdu_parser.py`) — дополни тестами на связь CVE↔БДУ.
> - `enrich()` на фикстуре: находка с `CVE-2013-5946` получает связанный `BDU:…`;
>   находка только с сервис+версия получает CVE и БДУ по CPE. Тесты обязательны.
> - Работает на SQLite-фикстуре или с мок-репозиторием (не требуй живой Postgres в
>   тестах). Образец выгрузки БДУ лежит вне репозитория, путь — в `BDU_FSTEC_FEED_PATH`.
> - Не коммить сам файл выгрузки (34 МБ) в репозиторий.

### T1 — Persistence и реальное ядро
> Задача: сделать слой БД и ядро рабочими.
> Владеешь: `scanner/core/db.py` (engine/session, SQLAlchemy 2.0), `scanner/core/repository.py`
> (функции сохранения `scan_runs`, `host_results`, `service_results`, `findings`,
> чтение находок прогона для diff/отчётов), `alembic/` (инициализировать Alembic из
> `db/migrations/0001_initial.sql` как первую миграцию), доработка `core/audit.py`
> (`AuditSink`, пишущий в таблицу `audit_log`).
> Критерии приёмки: миграции применяются на чистый Postgres из compose; round-trip
> тест «сохранить находки → прочитать обратно»; аудит пишется в БД.

### T3 — Discovery / инвентаризация (nmap)
> Задача: реализовать `DiscoveryModule.run()` на nmap.
> Владеешь: `scanner/modules/discovery.py`, тесты с образцом nmap XML.
> Что сделать: сформировать и выполнить вызов nmap (`-sV -O`) по `ctx.targets` (уже
> отфильтрованы allowlist-ом) с учётом `ctx.rate` (параллелизм/скорость), записать
> команду в `ctx.audit`, распарсить XML (`python-libnmap`) в `ServiceInfo` (положить
> в `ctx.services`) и вернуть info-`Finding` по хостам/портам/ОС.
> Критерии приёмки: парсинг эталонного nmap XML в `ServiceInfo` покрыт тестом (без
> реального сканирования в CI); соблюдены лимиты и аудит.

### T6 — Отчёты и рекомендации по устранению
> Задача: реализовать рендер отчётов с **понятными рекомендациями по устранению**.
> Владеешь: `scanner/reporting/render.py`, `scanner/reporting/templates/`, доработка
> `reporting/diff.py` при необходимости.
> Что сделать: по списку `Finding` построить отчёт в форматах **HTML (Jinja2) → PDF
> (WeasyPrint), DOCX (python-docx), JSON**. Разрезы: по каждому модулю раздельно,
> сводный по всем модулям, и **тренд между прогонами** (используя `diff_runs`:
> open/fixed/new/regression + динамика по severity). В каждой находке показывать
> **рекомендацию по устранению**: из меры БДУ (`remediation`), мер NVD/вендора,
> правила бенчмарка (для config audit). Группировка по severity, краткое summary
> для руководителя + детальная часть для инженеров.
> Критерии приёмки: генерация всех 4 форматов на фикстуре находок; в отчёте есть
> секция рекомендаций и раздел сравнения с предыдущим прогоном; тесты на структуру
> JSON и на наличие рекомендаций.

### T4 — Поиск уязвимостей (Nuclei) — волна 2
> Задача: `VulnModule.run()` на Nuclei. Владеешь: `scanner/modules/vuln.py`.
> Запуск Nuclei по `ctx.services`/`ctx.targets` с лимитами и аудитом, нормализация
> вывода в `Finding`, обогащение через `feeds.matcher.VulnMatcher.enrich` (интерфейс
> из T2). Строить на фикстурах, не требуя живого Nuclei в CI. Тесты на нормализацию.

### T5 — Аудит конфигураций (безагентный) — волна 2
> Задача: `ConfigAuditModule.run()` **безагентно по SSH**. Владеешь:
> `scanner/modules/config_audit.py`. OpenSCAP через `oscap-ssh` (профили CIS и под
> требования ФСТЭК/ГОСТ) и/или Lynis по SSH без постоянного агента; результаты →
> `Finding(finding_type=CONFIG)` с привязкой к правилу бенчмарка и рекомендацией.
> SSH-доступы — параметры engagement; все подключения в аудит. Тесты на парсинг
> эталонного вывода OpenSCAP/Lynis.

### T7 — API, RBAC и оркестрация — волна 2
> Задача: FastAPI-слой и роли. Владеешь: `scanner/api/*`, `scanner/core/orchestrator.py`.
> Эндпоинты: engagements/allowlist (CRUD), запуск/остановка прогона, получение
> отчётов. RBAC: admin/operator/auditor + отдельное право `cred_audit`. Проверка прав
> до постановки задач. Подключить оркестратор к репозиторию T1. Тесты на RBAC и на
> то, что запуск прогона отбрасывает цели вне allowlist.

### T8 — Аудит учётных данных (контролируемый) — волна 3
> Задача: `CredentialAuditModule.run()` — контролируемая проверка слабых/дефолтных
> учёток на allowlist-хостах. Владеешь: `scanner/modules/cred_audit.py`.
> Жёсткие лимиты (`ctx.rate.max_auth_attempts_per_target`, backoff), остановка при
> признаках блокировки, без встроенных словарей (набор учёток задаёт оператор),
> каждая попытка — в аудит. Включается отдельным правом. Тесты на соблюдение лимитов
> и на остановку при lockout.

## 5. Порядок запуска

1. Смёржить PR #1 в `main` (ревью за заказчиком).
2. Запустить **волну 1**: T1, **T2 (приоритет)**, T3, T6 — 4 параллельных треда.
3. По мере готовности интерфейсов волны 1 — **волна 2**: T4, T5, T7.
4. **Волна 3**: T8 + сквозная интеграция и отчёт-тренд.

Координатор проекта создаёт по треду на задачу с соответствующим промтом. Каждый
тред ведёт свой PR; интеграция — через `main`.
