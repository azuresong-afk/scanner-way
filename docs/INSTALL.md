# Установка и первый запуск

Пошаговая инструкция оператора: от чистой Linux-машины до первого отчёта с
привязкой находок к БДУ ФСТЭК. После установки пройдите чек-лист
[`TESTING.md`](TESTING.md).

> Сканер предназначен только для авторизованного тестирования по договору.
> Запускайте прогоны только по адресам, на которые есть письменное разрешение
> владельца, и только после того, как эти адреса внесены в allowlist договора.

## 1. Требования

| Что | Минимум |
|---|---|
| ОС | Linux x86_64 (Debian 12 / Ubuntu 22.04+ или аналог) |
| Docker | Docker Engine 24+ с плагином Compose v2 (`docker compose version`) |
| Ресурсы | 2 vCPU, 4 ГБ ОЗУ, 20 ГБ диска (БД со справочниками занимает несколько ГБ) |
| Сеть при установке | доступ к Docker Hub, PyPI, npm, GitHub (Nuclei и его шаблоны) |
| Сеть при работе | маршрут до целей из договора; для NVD — доступ к `services.nvd.nist.gov` |
| Порты на хосте | по умолчанию 8080 (веб), 8000 (API), 5432 (PostgreSQL); если заняты — меняются в `.env`, см. [раздел 5.1](#51-если-на-машине-уже-работают-другие-контейнеры) |

Образ собирается под `linux/amd64`. Для ARM-сервера соберите с
`--build-arg TARGETARCH=arm64`.

Проверка:

```bash
docker --version
docker compose version
```

## 2. Получение кода

```bash
git clone https://github.com/azuresong-afk/scanner-way.git
cd scanner-way
```

Все дальнейшие команды выполняются из этого каталога.

## 3. Настройка `.env`

```bash
cp .env.example .env
```

Откройте `.env` и замените все значения `CHANGE_ME…`:

| Переменная | Что задать |
|---|---|
| `POSTGRES_PASSWORD` | пароль БД, любой стойкий |
| `SCANNER_API_SECRET` | ключ подписи токенов, не короче 32 символов: `openssl rand -base64 48` |
| `SCANNER_API_BOOTSTRAP_ADMIN` | логин первого администратора (по умолчанию `admin`) |
| `SCANNER_API_BOOTSTRAP_PASSWORD` | пароль первого администратора, не короче 12 символов |

Остальное можно оставить как есть:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BDU_FSTEC_FEED_PATH` | `/data/vullist.xlsx` | путь к выгрузке БДУ внутри контейнера (это `./data` на хосте) |
| `SCANNER_BDU_AUTOLOAD` | `1` | загрузить БДУ автоматически при первом старте |
| `SCANNER_NUCLEI_UPDATE` | `1` | обновлять шаблоны Nuclei при старте. Шаблоны хранятся в томе `nuclei_templates`; без сети обновление пропускается, ошибка видна в логах `app` |
| `NVD_API_KEY` | пусто | ключ NVD API 2.0, ускоряет загрузку CVE ([получить](https://nvd.nist.gov/developers/request-an-api-key)) |
| `BDU_FSTEC_FEED_URL` | пусто | если задан, автообновление скачивает выгрузку БДУ по этому адресу; пусто — берётся файл `BDU_FSTEC_FEED_PATH` (в закрытом контуре обновляйте файл вручную, а расписание сверит его отпечаток и загрузит, только если он изменился) |
| `NUCLEI_TEMPLATES_DIR` | `$HOME/nuclei-templates` | каталог шаблонов Nuclei (для подсчёта шаблонов после обновления) |
| `ADVISORY_RELEASES` | `debian:bullseye,debian:bookworm,ubuntu:focal,ubuntu:jammy,ubuntu:noble,rhel:8,rhel:9,alt:p10` | выпуски ОС, для которых загружаются бюллетени дистрибутивов (учёт бэкпортов, см. раздел 7). Оставьте только те, что есть у заказчика: файлы большие |
| `ADVISORY_DIR` | `/data/advisories` | каталог файлов бюллетеней (`./data/advisories` на хосте); файл здесь главнее адреса — так работает закрытый контур |
| `ADVISORY_URL_<СЕМЕЙСТВО>` | пусто | свой адрес выгрузки семейства (`DEBIAN`, `UBUNTU`, `RHEL`, `ALT`, `ASTRA`, `REDOS`), `{release}` подставляется. Пусто — адрес вендора; у Astra Linux и РЕД ОС его нет |
| `SCANNER_API_FEEDS_TICK_SECONDS` | `60` | как часто планировщик справочников проверяет расписание; `0` — выключить автообновление |
| `DEFAULT_RATE_PROFILE` | `gentle` | профиль нагрузки по умолчанию |
| `SCANNER_CREDENTIALS_KEY` | пусто | ключ шифрования учётных записей активов (паролей и ключей SSH), не короче 16 символов. Пусто — берётся `SCANNER_API_SECRET`. Лучше задать отдельно и сохранить: при смене ключа сохранённые учётки перестают расшифровываться, их придётся завести заново |
| `SCANNER_SSH_KNOWN_HOSTS` | `/data/ssh_known_hosts` | ключи SSH хостов, запомненные при первом входе (`./data` на хосте). Если ключ хоста потом изменится, вход на него не выполняется |
| `SCANNER_API_TIMEZONE` | `Europe/Moscow` | часовой пояс расписаний, если браузер оператора не сообщил свой |
| `SCANNER_API_SCHEDULER_TICK_SECONDS` | `30` | как часто планировщик проверяет расписания; `0` — выключить запуск по расписанию |
| `SCANNER_SSH_STRICT_HOST_KEYS` | `0` | `1` — входить только на хосты, чей ключ уже есть в файле выше (заполнить заранее: `ssh-keyscan`) |
| `SCANNER_CONFIG_AUDIT_SCAP_DIR` | `/usr/share/xml/scap/ssg/content` | каталог контента SCAP Security Guide (`ssg-*-ds.xml`) для аудита конфигураций; свой контент можно положить в `./data/ssg` и указать `/data/ssg` |
| `SCANNER_CONFIG_AUDIT_SCAP_CONTENT` | пусто | свой datastream (например, профиль ФСТЭК/ГОСТ) для всех хостов вместо выбора по ОС |
| `SCANNER_CONFIG_AUDIT_SCAP_PROFILE` | пусто | профиль XCCDF; пусто — первый из CIS уровня 1 для серверов / standard, который есть в datastream |
| `SCANNER_CONFIG_AUDIT_LYNIS_BUNDLE` | пусто | архив Lynis (`lynis-*.tar.gz` с каталогом `lynis/`); пусто — Lynis из образа |
| `SCANNER_CONFIG_AUDIT_COMMAND_TIMEOUT_SEC` | `1800` | предел времени одной проверки (OpenSCAP или Lynis) на хосте; по истечении движок на хосте останавливается |

Быстро сгенерировать секреты:

```bash
sed -i "s|^SCANNER_API_SECRET=.*|SCANNER_API_SECRET=$(openssl rand -base64 48 | tr -d '\n')|" .env
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$(openssl rand -hex 24)|" .env
sed -i "s|^SCANNER_CREDENTIALS_KEY=.*|SCANNER_CREDENTIALS_KEY=$(openssl rand -base64 48 | tr -d '\n')|" .env
grep CHANGE_ME .env    # не должно остаться ничего, кроме пароля админа, если задаёте его вручную
```

Файл `.env` содержит секреты и в git не попадает (`.gitignore`). Ограничьте
доступ: `chmod 600 .env`.

## 4. Выгрузка БДУ ФСТЭК

Привязка находок к БДУ ФСТЭК — главная функция продукта, поэтому выгрузку
лучше положить до первого запуска.

1. Скачайте `vullist.xlsx` с сайта БДУ ФСТЭК (bdu.fstec.ru, раздел
   «Уязвимости», выгрузка списка в Excel).
2. Положите файл в каталог `data` репозитория:

```bash
cp /путь/к/vullist.xlsx ./data/vullist.xlsx
```

При первом старте контейнер загрузит его сам (около 2 минут на ~98 600
записей) и создаст метку `data/.bdu_loaded`, чтобы не грузить повторно.
Если файл положить позже, загрузите его командой из раздела 7.

## 5. Запуск

Если на машине уже работают другие контейнеры или службы, сначала пройдите
[раздел 5.1](#51-если-на-машине-уже-работают-другие-контейнеры): там проверка
портов и сетей до запуска. На чистой машине можно сразу запускать.

```bash
docker compose up --build -d
docker compose logs -f app
```

Первая сборка занимает 5–15 минут (зависит от сети). Поднимаются три сервиса:

| Сервис | Что это | Адрес |
|---|---|---|
| `web` | веб-интерфейс (nginx), проксирует `/api/*` на `app` | http://<сервер>:8080, открыт для сети |
| `app` | API сканера + движки nmap, Nuclei, OpenSCAP, Lynis | http://127.0.0.1:8000, только с самого сервера |
| `db` | PostgreSQL 16, данные в томе `pg_data` | 127.0.0.1:5432, только с самого сервера |

Номера портов выше — значения по умолчанию; если вы поменяли их в `.env`,
подставляйте свои.

В логах `app` должны пройти по порядку:

```
[entrypoint] применяю миграции схемы БД (alembic upgrade head)...
[entrypoint] одноразовая загрузка выгрузки БДУ ФСТЭК из /data/vullist.xlsx...
БДУ ФСТЭК: загружено записей — 98617          (если файл положен)
[entrypoint] обновляю шаблоны Nuclei (по возможности)...
[entrypoint] запускаю API на :8000 ...
INFO:     Uvicorn running on http://0.0.0.0:8000
```

Проверка живости:

```bash
curl -s http://localhost:8000/health      # {"status":"ok"}
curl -s http://localhost:8080/healthz     # ok
docker compose ps                         # все три сервиса в состоянии running / healthy
```

Если сервер доступен по сети, откройте `http://<ip-сервера>:8080`.

### 5.1. Если на машине уже работают другие контейнеры

Сканер живёт в собственном проекте compose и с чужими контейнерами делит
только три вещи: порты хоста, имена и адреса сетей Docker. Проверьте их до
первого `docker compose up`.

**Шаг 1. Порты.** Посмотрите, что уже слушает 8080, 8000 и 5432:

```bash
sudo ss -ltnp | grep -E ':(8080|8000|5432)\b'
docker ps --format '{{.Names}}\t{{.Ports}}' | grep -E '(8080|8000|5432)->'
```

Пустой вывод значит, что порты свободны. Если какой-то занят, задайте в
`.env` свободные порты хоста (внутри контейнеров ничего не меняется):

```bash
# пример: 8080 и 5432 уже заняты другими контейнерами
SCANNER_WEB_PORT=18080
SCANNER_API_PORT=18000
SCANNER_DB_PORT=15432
```

Проверьте, что новые тоже свободны (`sudo ss -ltnp | grep -E ':(18080|18000|15432)\b'`
ничего не выводит). Веб-интерфейс тогда будет на `http://<сервер>:18080`,
API для проверок — `http://127.0.0.1:18000/health`.

API и БД публикуются только на `127.0.0.1` хоста, поэтому снаружи они не
видны и с сервисами на других интерфейсах не конфликтуют. Для работы
сканера они наружу и не нужны: веб обращается к API по внутренней сети
compose.

**Шаг 2. Имя проекта.** Контейнеры, сеть и том БД получают префикс по имени
каталога: `scanner-way-app-1`, `scanner-way_default`, `scanner-way_pg_data`.
Убедитесь, что таких ещё нет:

```bash
docker ps -a --format '{{.Names}}' | grep '^scanner-way' ; docker volume ls | grep scanner-way
```

Если что-то нашлось (например, от прошлой установки), либо удалите старое,
либо задайте своё имя проекта первой строкой в `.env`:
`COMPOSE_PROJECT_NAME=scanner`. Тогда префикс будет `scanner-`, и в
командах этой инструкции `scanner-way` меняйте на `scanner`.

**Шаг 3. Подсети Docker.** Docker сам выбирает свободную подсеть для сети
проекта, тут ничего делать не нужно. Подсеть понадобится только для
учебного стенда из раздела 10: проверьте, что `172.30.0.0/24` не занята ни
сетями Docker, ни вашей локальной сетью:

```bash
docker network inspect $(docker network ls -q) \
    --format '{{.Name}} {{range .IPAM.Config}}{{.Subnet}} {{end}}' | grep '172\.30\.'
ip route | grep '172\.30\.'
```

Пустой вывод — подсеть свободна. Если занята, возьмите другую, например
`10.250.0.0/24`, и везде в разделе 10 замените адреса на неё.

**Шаг 4. Ресурсы.** Сканер в простое занимает около 1 ГБ ОЗУ, во время
прогона больше. На общей машине проверьте запас: `free -h`, `df -h`.

После этого запускайте как обычно (`docker compose up --build -d`). Чужие
контейнеры compose не трогает: команды `docker compose ...` из каталога
сканера работают только с его сервисами. Исключение — `docker compose
down -v`: она удалит том БД **сканера**, но не чужие тома.

## 6. Первый вход

1. Откройте http://localhost:8080.
2. Войдите логином и паролем из `SCANNER_API_BOOTSTRAP_ADMIN` /
   `SCANNER_API_BOOTSTRAP_PASSWORD`.
3. Слева — меню разделов, внизу меню — переключатель светлой/тёмной темы.

Администратор создаётся только один раз, пока в БД нет ни одного
пользователя. После первого входа переменные `SCANNER_API_BOOTSTRAP_*` можно
убрать из `.env`: смена пароля в `.env` на уже созданного админа не влияет.

## 7. Справочники: БДУ и NVD

**БДУ ФСТЭК.** Проверить, что загрузилась, и при необходимости загрузить
вручную (например, свежую выгрузку раз в неделю):

```bash
docker compose exec app scanner feeds sync-bdu --file /data/vullist.xlsx
```

Повторная загрузка безопасна: записи обновляются, дублей не будет.

**Автообновление по расписанию.** БДУ, NVD и шаблоны Nuclei можно обновлять сами:
раздел «Справочники» (роль admin) → ✎ у нужного справочника → включить и задать
время. По умолчанию расписание выключено — сканер не ходит в интернет без вашего
ведома. NVD после первой полной загрузки обновляется инкрементально (только
изменённые с прошлого раза CVE, окно нарезается по лимиту NVD). Если расписание
включено, `entrypoint` при старте контейнера не дублирует обновление шаблонов
Nuclei (БДУ при старте только досевает пустую базу). Кнопка «Обновить сейчас»
запускает загрузку вне расписания.

**NVD (CVE, CVSS, CPE).** Необязательно для привязки к БДУ (связь CVE→БДУ
берётся из самой выгрузки БДУ), но даёт CVSS и описания CVE:

```bash
# полная загрузка: десятки минут без ключа, быстрее с NVD_API_KEY
docker compose exec app scanner feeds sync-nvd

# инкрементально за период (окно NVD — не больше 120 дней)
docker compose exec app scanner feeds sync-nvd --since 2026-09-01 --until 2026-10-28

# одна CVE — удобно для проверки
docker compose exec app scanner feeds sync-nvd --cve CVE-2021-41773

# офлайн: заранее скачанные фиды NVD 2.0
docker compose exec app scanner feeds sync-nvd --file /data/nvdcve-2.0-2024.json.gz
```

**Бюллетени дистрибутивов (учёт бэкпортов).** Нужны поиску уязвимостей по
учётной записи: дистрибутивы закрывают уязвимости в своих ревизиях пакетов, не
меняя версию апстрима (openssl `3.0.11-1~deb12u2` в Debian 12, openssh
`1:9.2p1-2+deb12u3`). С бюллетенями сканер сравнивает точную версию пакета с
версией, в которой вендор исправил CVE, и не показывает уже закрытое.

| Семейство | Источник | Выпуск в `ADVISORY_RELEASES` |
|---|---|---|
| `debian` | трекер безопасности Debian (один JSON на все выпуски) | `bookworm`, `bullseye`… |
| `ubuntu` | OVAL бюллетеней USN, файл на выпуск | `jammy`, `noble`… |
| `rhel` | OVAL v2 Red Hat; им же сверяются CentOS, Rocky, AlmaLinux, Oracle Linux, МСВСфера | `8`, `9` |
| `alt` | OVAL errata ALT (zip) | `p10`, `p11` |
| `astra` | OVAL вендора — адреса по умолчанию нет, файл кладёт оператор | `1.7`, `1.8` |
| `redos` | OVAL вендора — адреса по умолчанию нет, файл кладёт оператор | `7.3`, `8` |

```bash
# по ADVISORY_RELEASES (с интернетом или из ./data/advisories)
docker compose exec app scanner feeds sync-advisories

# отдельные выпуски / свой файл
docker compose exec app scanner feeds sync-advisories --release debian:bookworm
docker compose exec app scanner feeds sync-advisories --release astra:1.7 \
    --file /data/advisories/astra-1.7.xml
```

В закрытом контуре скачайте файлы на машине с интернетом и положите в
`./data/advisories` под именами `debian.json` (или `.json.gz`),
`ubuntu-jammy.xml.bz2`, `rhel-9.xml.bz2`, `alt-p10.zip`, `astra-1.7.xml`,
`redos-7.3.xml` — сжатие определяется по содержимому. Тот же источник есть в
«Справочниках» («Бюллетени дистрибутивов»), его можно поставить на расписание.

Если для выпуска ОС хоста бюллетеней нет, находки остаются как раньше (по
версии апстрима) с пометкой «Нет данных вендора» в доказательстве.

Каждая загрузка пишется в журнал аудита (`feed_sync`).

## 8. Пользователи и роли

Администратор по замыслу **не запускает прогоны** (разделение обязанностей),
поэтому сразу заведите оператора.

Раздел **«Пользователи и роли»** → «Создать пользователя»:

| Роль | Что может |
|---|---|
| `admin` | пользователи и роли, договоры, allowlist, журнал аудита, просмотр отчётов |
| `operator` | запуск и остановка прогонов, просмотр находок и отчётов, отметка ложных срабатываний (право `triage_findings`) |
| `auditor` | только просмотр, выгрузка отчётов, журнал аудита |
| `cred_audit` | отдельное право на модуль аудита учётных данных; выдаётся вдобавок к `operator` только при наличии согласования в договоре |
| `host_credentials` | отдельное право на учётные записи активов: заводить их в договоре и запускать с ними поиск уязвимостей «По учётной записи» (раздел 10). Выдаётся вдобавок к `operator`, когда заказчик передал доступы |

Рекомендуемый минимум: `admin` (вы), `operator` (тот, кто сканирует),
по желанию `auditor` (тот, кто принимает отчёты). Пароли — не короче 12
символов. Последнего активного администратора удалить или заблокировать
нельзя.

## 9. Договор и allowlist

Под администратором, раздел **«Договоры и allowlist»**:

1. «Новый договор»: название, заказчик, номер договора.
2. Откройте договор → «Добавить диапазон»: IP-адрес или подсеть в нотации
   CIDR (`192.0.2.10`, `192.0.2.0/28`), в примечании — основание (пункт
   договора, письмо).
3. Вносите только адреса, перечисленные в договоре или приложении к нему.

Сканер не тронет ни один адрес вне allowlist: такие цели отбрасываются до
запуска движков, отказ пишется в журнал аудита. Один прогон — не больше
4096 адресов.

## 10. Тестовый прогон

Для первой проверки нужна цель, которая принадлежит вам. Ниже — как
поднять её на той же машине, где стоит сканер, за пять минут. Чужие
контейнеры и порты эта схема не затрагивает.

### Как это устроено

```
                       сеть lab-net 172.30.0.0/24 (только для теста)
  ┌──────────────────┐        │        ┌────────────────────────────┐
  │ scanner-way-app-1│────────┼────────│ lab-web  172.30.0.10        │
  │ (сканер, API)    │        │        │ Apache 2.4.49 (уязвимый)    │
  └──────────────────┘                 └────────────────────────────┘
```

- Сканер работает внутри контейнера `app`, поэтому цель должна быть
  доступна **из этого контейнера**, а не только с хоста.
- Учебная цель `lab-web` — отдельный контейнер в отдельной сети `lab-net`.
  У него фиксированный адрес `172.30.0.10`: он не меняется при
  пересоздании, поэтому сравнение прогонов работает.
- Контейнер `app` дополнительно подключается к `lab-net`, чтобы видеть цель.
- У `lab-web` **нет** опубликованных портов (`-p` не используется), поэтому он
  не конфликтует с портами хоста и не виден из вашей сети.
- Цель — официальный образ `httpd:2.4.49` (Apache с CVE-2021-41773, обход
  каталога). Сама уязвимость эксплуатируется, только если в конфиге открыт
  доступ к корню ФС (`Require all granted` в `<Directory />`), а в образе по
  умолчанию стоит `denied`. Поэтому в шаге 2 конфиг меняется одной командой.
  Так Nuclei подтверждает CVE реальным запросом, а сопоставление по версии
  находит остальные уязвимости Apache 2.4.49 в БДУ.

### Шаг 1. Создать сеть стенда

Подсеть должна быть свободной (проверка — раздел 5.1, шаг 3).

```bash
docker network create --subnet 172.30.0.0/24 lab-net
```

Ожидаемо: команда печатает id сети. Ошибка `Pool overlaps with other one on
this address space` значит, что подсеть занята: возьмите другую (например
`10.250.0.0/24`) и дальше используйте её адреса.

### Шаг 2. Запустить учебную цель

```bash
docker run -d --name lab-web --network lab-net --ip 172.30.0.10 httpd:2.4.49
# открыть корень ФС в конфиге — условие эксплуатации CVE-2021-41773
docker exec lab-web sed -i '/<Directory \/>/,/<\/Directory>/ s/Require all denied/Require all granted/' \
    /usr/local/apache2/conf/httpd.conf
docker restart lab-web
docker ps --filter name=lab-web     # STATUS: Up
```

Если имя `lab-web` уже занято другим контейнером, выберите своё, например
`--name scanner-lab-web`, и используйте его дальше.

### Шаг 3. Подключить сканер к сети стенда

Команды выполняются из каталога сканера:

```bash
docker network connect lab-net "$(docker compose ps -q app)"
```

Проверка, что сканер видит цель (обычный HTTP-запрос из контейнера `app`):

```bash
docker compose exec app python -c \
  "import urllib.request; print(urllib.request.urlopen('http://172.30.0.10/').status)"
# 200
```

Проверка, что цель действительно уязвима (ожидается `b'root:x:0:0...`;
`403` значит, что правка конфига из шага 2 не применилась):

```bash
docker compose exec app python -c "import urllib.request as u, urllib.error as e
try: print(u.urlopen('http://172.30.0.10/icons/.%2e/%2e%2e/%2e%2e/%2e%2e/etc/passwd').read()[:40])
except e.HTTPError as x: print(x.code)"
```

Подключение к `lab-net` сохраняется при `docker compose restart`, но
теряется при `docker compose down`/`up` и при `up --build` (контейнер
пересоздаётся). Тогда просто повторите эту команду.

### Шаг 4. Внести цель в договор

Под **администратором**:

1. «Договоры и allowlist» → «Новый договор», например «Тестовый стенд».
2. В договоре «Добавить диапазон»: `172.30.0.10/32`, примечание «учебный
   стенд, собственный».

### Шаг 5. Запустить прогон

Под **оператором** (администратор прогоны не запускает, см. раздел 8):

1. Раздел **«Прогоны»** → «Запустить прогон», выберите «Тестовый стенд».
2. Цели: `172.30.0.10`.
3. Модули: «Обнаружение и инвентаризация» и «Поиск уязвимостей».
4. Профиль нагрузки: для своей учебной цели — `normal`; `gentle` (щадящий)
   оставьте для сетей заказчика (о времени см. ниже).
5. Отметьте подтверждение, что цели входят в объём работ по договору.
6. «Запустить». Откроется карточка прогона со статусом в реальном времени:
   `pending` → `running` → `done`.

Сколько ждать. Обнаружение (nmap, 1000 портов) занимает около 5 минут. Поиск
уязвимостей прогоняет по каждому найденному сервису все шаблоны Nuclei, а
это тысячи запросов, поэтому его время определяет профиль. На одну цель с
одним веб-сервисом `normal` занимает 10–15 минут, а `gentle` — около часа.
Время растёт пропорционально числу сервисов. Таймаут Nuclei считается от
профиля и числа целей. Если он всё же сработает, найденное до обрыва
сохраняется, а у хоста появляется информационная находка «Поиск
уязвимостей прерван по таймауту — результаты неполные».

Ожидаемый результат: в «Хостах» у `172.30.0.10` порт 80 с Apache httpd
2.4.49, в «Находках» — уязвимости этого Apache, среди них `CVE-2021-41773` с
идентификатором `BDU:…`. Подробная проверка — [`TESTING.md`](TESTING.md),
шаги 7–8.

Профили нагрузки:

| Профиль | Запросов/с | Параллельно | Попыток входа на цель (cred_audit) |
|---|---|---|---|
| `gentle` | 5 | 8 | 3 |
| `normal` | 20 | 32 | 5 |
| `aggressive` | 100 | 128 | 8 |

Остановить прогон можно кнопкой «Остановить» в карточке прогона.

### Поиск уязвимостей по учётной записи

Кроме Nuclei, у поиска уязвимостей есть второй движок — **по учётной
записи**. Сканер входит на хост по SSH (пароль или ключ), выполняет команды
только на чтение (`/etc/os-release`, `uname`, список пакетов dpkg / rpm /
apk, без `sudo`) и сопоставляет версии установленных пакетов с БДУ ФСТЭК и
CVE/NVD. Он находит уязвимости ПО, которое не слушает порт и не видно снаружи
(OpenSSL, glibc, sudo, polkit, xz и т. д.).

Движок выбирается в форме запуска, в блоке «Поиск уязвимостей — движок»:

| Вариант | Что запускается |
|---|---|
| Nuclei | сетевые проверки снаружи, без учётной записи (как раньше) |
| По учётной записи | вход по SSH и сопоставление пакетов; нужна учётка |
| Оба движка | и то и другое в одном прогоне |
| Не искать | только остальные выбранные модули |

Как включить:

1. Под администратором выдайте оператору право `host_credentials` (раздел 8).
2. Оператор: страница договора → «Учётные записи активов» → «Добавить».
   Логин на хосте, порт SSH, пароль или закрытый ключ (Ed25519, ECDSA, RSA;
   можно загрузить файлом, с парольной фразой). «Область действия» — IP и
   подсети, к которым подходит учётка; только из allowlist договора. Пусто —
   все цели прогона.
3. «Запустить прогон» → движок «По учётной записи» или «Оба движка» →
   отметьте учётки → «Запустить». На каждый хост пробуются подходящие
   учётки, начиная с самой узкой области, не больше трёх.

Что получится: на странице хоста ОС из `/etc/os-release` и список
установленных пакетов; в «Находках» модуль «Уязвимости (учётка)» с `BDU:…`
и CVE по каждому уязвимому пакету.

Безопасность:

- пароли и ключи хранятся в БД зашифрованными (`SCANNER_CREDENTIALS_KEY`,
  раздел 3) и никогда не отдаются API, не пишутся в журнал аудита и логи. В
  журнал попадают только название учётки, логин, порт и отпечаток ключа;
- без права `host_credentials` нельзя ни завести учётку, ни запустить с ней
  прогон (403, в журнале `access_denied`);
- учётка не выходит за allowlist договора, а прогон — за allowlist, как и
  остальные модули; учётку другого договора выбрать нельзя;
- ключ хоста запоминается при первом входе (`SCANNER_SSH_KNOWN_HOSTS`); если
  он потом изменится, вход не выполняется, в находках «Ключ SSH хоста не
  прошёл проверку»;
- поиску уязвимостей по учётной записи достаточно обычных прав пользователя:
  `sudo` он не использует (права root нужны только аудиту конфигураций,
  см. ниже).

Как читать находки. Сопоставление идёт по версии апстрима. Дистрибутивы
часто закрывают уязвимости бэкпортом, не меняя основную версию пакета
(Debian 12: openssh `1:9.2p1-2+deb12u3` — это всё ещё `9.2p1`). Такие
находки помечены в доказательстве; сверяйте их с бюллетенем дистрибутива.
Ядро по версии не сопоставляется. Проверка на стенде —
[`TESTING.md`](TESTING.md), шаг 8а.

### Аудит конфигураций по учётной записи

Модуль «Аудит конфигураций» проверяет настройки хоста по CIS Benchmarks и, при
своём контенте, по требованиям ФСТЭК/ГОСТ. Он использует те же учётные записи
договора, но ему нужны права root.

Как работает на каждом хосте:

1. Вход по SSH учёткой договора: сначала с самой узкой областью действия, при
   отказе — следующая, не больше трёх.
2. Чтение `/etc/os-release` без `sudo`, затем проверочный `sudo true`.
3. Выбор проверки по ОС: Debian, Ubuntu, RHEL, Oracle, AlmaLinux, CentOS
   Stream, Fedora, SLES — OpenSCAP с контентом SCAP Security Guide (профиль
   CIS уровня 1 для серверов, иначе standard) и Lynis; Astra Linux, РЕД ОС,
   Альт и другие — только Lynis. Нет `oscap` на хосте — только Lynis.
4. Временный каталог `/tmp/scanner-cfg.*` (права 0700), контент передаётся
   по SFTP, проверка запускается под `sudo` с ограничением по времени,
   каталог удаляется после проверки, даже при ошибке. Если связь оборвалась,
   сканер удаляет каталог в отдельном соединении и пишет итог в журнал.

Повышение прав задаётся в учётке («Повышение прав»; в CLI — `--become`):

| Значение | Что делает |
|---|---|
| `sudo` (по умолчанию) | учётка с паролем: `sudo -S`, пароль подаётся через stdin соединения — его нет ни в командной строке, ни в журнале. Учётка с ключом: `sudo -n`, нужен `NOPASSWD` в sudoers, иначе понятная ошибка «sudo требует пароль» |
| `none` | без `sudo`: подходит для входа сразу под root; под обычным пользователем часть правил не проверится |

Как включить: право `host_credentials` (раздел 8), учётка договора, в форме
запуска модуль «Аудит конфигураций» и учётки в блоке «Учётные записи для
входа на хосты». Без учётки прогон не запускается.

Что получится: по каждому хосту информационная находка-сводка (ОС, профиль,
учётка, способ повышения прав, почему OpenSCAP не запускался, если так) и
нарушения `[OpenSCAP] …` / `[Lynis …]` с рекомендацией из правила бенчмарка и
ссылками на документы. Хост, к которому не подошла ни одна учётка, получает
находку «нет учётной записи для хоста». Проверка на стенде —
[`TESTING.md`](TESTING.md), шаг 9.

### Если прогон ничего не нашёл

| Что видно | Причина и что сделать |
|---|---|
| Прогон не создаётся: «ни одна цель не входит в allowlist» | адреса нет в allowlist выбранного договора (шаг 4) |
| `done`, но в «Хостах» пусто | сканер не видит цель: повторите шаг 3 и проверку из него |
| Порт найден, уязвимостей нет | не скачаны шаблоны Nuclei: `docker compose exec app nuclei -update-templates`, затем прогон заново |
| Уязвимости есть, но без БДУ | не загружена выгрузка БДУ (раздел 7) |
| Движок «По учётной записи»: «Вход по учётной записи отклонён» | неверный логин, пароль или ключ; проверьте вход вручную `ssh -p <порт> <логин>@<адрес>` с сервера сканера |
| «Ключ SSH хоста не прошёл проверку» | ключ хоста изменился с прошлого входа. Если это ожидаемо (переустановка), удалите строку хоста: `docker compose exec app sed -i '/^<адрес> /d' /data/ssh_known_hosts` |
| «Хост недоступен по SSH» | порт SSH закрыт или фильтруется; проверьте порт учётки |
| Пакетов 0 | на хосте нет dpkg / rpm / apk (не Linux или нестандартная сборка) |

### Шаг 6. Убрать стенд после проверок

```bash
docker rm -f lab-web
docker network disconnect lab-net "$(docker compose ps -q app)"
docker network rm lab-net
```

Сканер и его данные остаются; удаляется только учебная цель и её сеть.

### Сканирование реальной сети заказчика

Здесь ничего дополнительно разворачивать не нужно. Контейнер `app` ходит в
сеть через сетевой стек хоста, поэтому видит всё, что видит сам сервер
сканера. Проверьте маршрут до целей с хоста (`ip route get <адрес цели>`),
внесите адреса из договора в allowlist и запускайте прогон как в шаге 5.

## 11. Находки и привязка к БДУ

- **«Сводка»** — открытые уязвимости последнего прогона по уровням опасности,
  доля сопоставленных с БДУ, изменения к прошлому прогону, самые уязвимые
  хосты, приоритетные уязвимости.
- **«Находки»** — фильтры по опасности, модулю, статусу и наличию БДУ, поиск
  по CVE/БДУ/хосту. Клик по строке открывает карточку: описание,
  идентификаторы `BDU:ГГГГ-NNNNN` и `CVE-…`, CVSS, доказательство,
  рекомендации и ссылки на БДУ ФСТЭК, NVD, бюллетени вендора.
- **«Хосты»** — по каждому хосту: ОС, открытые порты и сервисы с версиями,
  все его уязвимости. Хосты можно отфильтровать и сгруппировать по ОС
  (см. ниже).

### ОС хостов: фильтр и группировка

Сканер определяет ОС каждого хоста по данным прогонов и сводит её к
семейству: Astra Linux, РЕД ОС, Альт, РОСА, МСВСфера, Ubuntu, Debian,
CentOS / RHEL / Rocky / AlmaLinux / Oracle Linux, Fedora, SUSE, Alpine,
Windows, macOS, BSD, сетевое оборудование. Источники — по убыванию
точности:

| Источник | Откуда | Что даёт |
|---|---|---|
| Учётная запись | `/etc/os-release` на хосте (движок «По учётной записи») | Точный дистрибутив и версию: `Astra Linux SE 1.7`, `RED OS MUROM (7.3.4)` |
| Баннеры сервисов | `nmap -sV` (модуль «Обнаружение») | Дистрибутив, если сервис его называет: `OpenSSH 8.9p1 Ubuntu…`, `Apache (Debian)` |
| Отпечаток стека | `nmap -O` (модуль «Обнаружение») | Только ядро: «Linux 4.15 - 5.8», «Windows Server 2016» — дистрибутив Linux так не различить |

Поэтому **Astra Linux и РЕД ОС надёжно определяются только по учётной
записи**: без неё такой хост попадёт в группу «Linux (дистрибутив не
определён)» или, если sshd называет базовый дистрибутив, — в Debian.
Подсказка у названия ОС в таблице говорит, откуда оно взято.

Во вкладке **«Хосты»** под заголовком — чипы семейств с числом хостов
(нажатие оставляет только эти ОС, можно выбрать несколько), флажок
**«По ОС»** делит таблицу на группы с суммарным распределением уязвимостей
выбранного прогона (выбор запоминается в браузере). Поиск тоже ищет по ОС.

ОС хоста берётся из самого точного источника по всем прогонам договора: если
прогон по учётке показал Astra, а следующий — только nmap «Linux», хост
остаётся в группе Astra. Если же nmap увидел другое семейство (хост
переустановлен под Windows), берётся новое.

API: `GET /engagements/{id}/hosts` возвращает `os_family`,
`os_family_label`, `os_source` (`ssh` | `banner` | `nmap`), `os_accuracy`;
параметр `?os_family=astra` фильтрует хосты (`unknown` — без ОС).

### Ложные срабатывания

Если находка на хосте не подтвердилась (например, исправление перенесено в
пакет дистрибутива — бэкпорт), оператор открывает её карточку и нажимает
**«Отметить как ложное срабатывание»**, по желанию указав обоснование.
Отметку снимает кнопка **«Снять отметку»** в той же карточке.

- Отметка ставится на конкретную находку конкретного хоста (хост + порт +
  идентификатор уязвимости + модуль) и действует во всех прогонах договора:
  в следующих прогонах эта находка сразу приходит отмеченной.
- Отмеченные находки не входят в «Сводку», счётчики по хостам, отчёты и
  сравнение прогонов (не считаются ни открытыми, ни устранёнными). В отчёте
  они перечислены отдельным последним разделом «Ложные срабатывания» —
  с обоснованием, автором и датой.
- В «Находках» их показывает флажок «Ложные срабатывания»; в карточке хоста и
  прогона — свёрнутый блок «Ложные срабатывания (N)».
- Отмечать и снимать отметку может роль `operator` (право `triage_findings`);
  аудитор и администратор видят отметки, но менять их не могут. Каждое
  действие пишется в журнал аудита (`false_positive_mark`,
  `false_positive_unmark`) с хостом, уязвимостью и обоснованием.
- API: `PUT /findings/{id}/false-positive` (тело `{"reason": "…"}`),
  `DELETE /findings/{id}/false-positive`, перечень отметок договора —
  `GET /engagements/{id}/false-positives`.

## 12. Отчёты

Раздел **«Отчёты»** (или меню отчёта в карточке прогона): просмотр HTML прямо
в интерфейсе и выгрузка в **PDF**, **Word (.docx)**, **HTML**, **JSON**.

В отчёте: обложка, сводка по опасности, разбор по хостам, по каждой
уязвимости — БДУ/CVE, рекомендации по устранению и ссылки на источники.
По умолчанию отчёт строится только по выбранному прогону. Чтобы добавить
сравнение (новые/закрытые/регрессии и тренд), выберите в списке
**«Сравнить с»** нужный более ранний успешно завершённый прогон того же
договора. Каждая выгрузка пишется в журнал аудита (действие `export`,
в деталях — `previous_run_id`).

### Выгрузка журнала аудита

Раздел **«Журнал аудита»** (роли `admin` и `auditor`, право `view_audit`):
задайте субъект, период «С/По» (или быстрые кнопки «24 часа», «7 дней»,
«30 дней») и нужные действия, затем нажмите **CSV** или **JSON**. Записи идут
от старых к новым, время в файле — UTC; конец периода не включается. CSV —
UTF-8 с BOM (открывается в Excel без кракозябр), JSON содержит шапку с
фильтром, автором выгрузки и числом записей. Журнал при этом только читается,
а сам факт выгрузки пишется в него же (действие `audit_export`). За один раз —
не больше 100 000 записей, иначе сузьте период.

Через API:

```bash
curl -H "Authorization: Bearer $TOKEN" -OJ \
  "http://localhost:8080/api/audit/export?format=csv&action=scan_start&action=deny&since=2026-10-01T00:00:00Z&until=2026-11-01T00:00:00Z"
```

`action` можно повторять; список встречающихся действий — `GET /api/audit/actions`.

## 13. Сравнение прогонов

Сравнение строится автоматически между прогонами одного договора: находка
определяется по хосту, порту, идентификатору уязвимости и модулю. Статусы:

| Статус | Значит |
|---|---|
| `new` | появилась впервые |
| `open` | была и осталась |
| `fixed` | была в прошлом прогоне, сейчас нет |
| `regression` | была исправлена ранее и появилась снова |

Видно на «Сводке» (новые/закрытые/регрессии, тренд), в фильтре статуса на
«Находках». В отчёт сравнение попадает только по запросу: опция **«Сравнить
с»** в меню отчёта, в API — `GET /api/runs/{id}/report?compare_to=<id>`, в CLI —
`scanner report --run <id> --compare-to <id>`. Чтобы увидеть сравнение,
запустите по тем же целям второй прогон.

## 13а. Прогоны по расписанию

Регулярные проверки не нужно запускать вручную. Раздел **«Расписания»** →
**«Новое расписание»** (или «Новый прогон» → «По расписанию»): та же форма,
что и у прогона — цели, движок, модули, учётки, профиль нагрузки, — плюс
периодичность:

| Вид | Когда запускается |
|---|---|
| Каждый день | ежедневно в указанное время |
| По дням недели | в выбранные дни (например, Пн и Пт) в указанное время |
| Раз в месяц | в указанное число; если в месяце его нет (31-е в феврале) — в последний день |
| Один раз | в указанные дату и время, после чего расписание выключается |

Время — в часовом поясе браузера оператора (он виден под полем и в списке),
моменты запуска хранятся в UTC, переходы на летнее время учитываются.

Как исполняется:

- Прогон ставит планировщик внутри контейнера `app` (проверка раз в
  `SCANNER_API_SCHEDULER_TICK_SECONDS`, по умолчанию 30 с), в журнале аудита —
  `schedule_fire` от имени `schedule:<id>` и обычный `scan_queue`.
- Запуск идёт **с правами того, кто последним сохранил расписание**: при
  каждом срабатывании они проверяются заново. Если пользователя отключили или
  у него больше нет нужных прав (`run_scan`, `cred_audit`, `host_credentials`),
  расписание выключается с отметкой «у владельца нет прав».
- Allowlist договора, как и для ручного прогона, перечитывается в момент
  запуска: цели, которые из него убрали, не сканируются.
- Если предыдущий прогон этого расписания ещё идёт, очередной запуск
  пропускается (видно в колонке «Последний запуск»).
- Если сканер был выключен во время запуска, после старта пропущенный прогон
  ставится один раз, без «догоняния» всех пропусков.

Кнопки в списке: **«Сейчас»** — поставить прогон немедленно, не сдвигая
график; карандаш — изменить; флажок «Включено» — приостановить/возобновить;
корзина — удалить (уже выполненные прогоны остаются). Прогоны по расписанию
отмечены в списках значком часов.

**Названия прогонов.** Вместо «Прогон №7» каждый прогон получает название по
выбранным опциям — что проверяем и где, например
`Обнаружение + Nuclei · 10.0.0.0/24` или
`Nuclei + учётная запись + конфигурации · 10.0.1.15, 10.0.1.16 и ещё 3`.
Своё название можно задать в поле «Название» формы (в CLI — `scanner run
--name "…"`); пусто — используется автоматическое. Прогоны, сделанные до
обновления, подписываются по модулям.

API: `GET/POST /api/engagements/{id}/schedules`, `GET/PUT/PATCH/DELETE
/api/schedules/{id}` (`PATCH {"enabled": false}` — выключить),
`POST /api/schedules/{id}/run` — запустить сейчас.

## 14. Работа из командной строки

Всё то же доступно через CLI внутри контейнера (договор и allowlist заводятся
только в вебе/API):

```bash
# прогон: обязательно подтверждение, что цели в рамках договора
docker compose exec app scanner --actor cli:ivanov run \
    --engagement 1 --targets 172.30.0.10 --modules discovery vuln \
    --rate gentle --confirm-authorized

# отчёт по завершённому прогону (файл появится в каталоге репозитория на хосте)
docker compose exec app scanner report --run 1 --format pdf --out /app/report-1.pdf
docker compose exec app scanner report --run 1 --format docx --out /app/report-1.docx
# краткая версия: без плана устранения, по находкам только ссылки на устранение
docker compose exec app scanner report --run 1 --format pdf --brief --out /app/report-1-brief.pdf
# отчёт по прогону 3 со сравнением с прогоном 1 (без флага — без сравнения)
docker compose exec app scanner report --run 3 --compare-to 1 --format pdf --out /app/report-3-vs-1.pdf

# учётные записи активов: пароль — из переменной окружения или запросом,
# ключ — из файла (в аргументах секрет не передаётся)
docker compose exec app scanner credentials add --engagement 1 --name "серверы ДМЗ" \
    --user audit --key-file /app/data/audit_key --targets 192.0.2.0/28
docker compose exec app scanner credentials add --engagement 1 --name "стенд" \
    --user audit --ask-password --targets 172.30.0.11
docker compose exec app scanner credentials list --engagement 1
docker compose exec app scanner credentials delete --engagement 1 --id 2

# прогон с движком «По учётной записи» (nuclei | credentialed | both)
docker compose exec app scanner --actor cli:ivanov run \
    --engagement 1 --targets 172.30.0.11 --modules discovery \
    --engine credentialed --credential 1 \
    --rate gentle --confirm-authorized --allow-credentials

# аудит конфигураций по учётной записи; --become sudo (по умолчанию) | none
docker compose exec app scanner credentials add --engagement 1 --name "аудит ДМЗ" \
    --user audit --ask-password --become sudo --targets 172.30.0.11
docker compose exec app scanner --actor cli:ivanov run \
    --engagement 1 --targets 172.30.0.11 --modules discovery config_audit \
    --credential 3 --rate gentle --confirm-authorized --allow-credentials
```

Без `--confirm-authorized` прогон не запускается. Модуль `cred_audit` в CLI
требует ещё и флаг `--allow-cred-audit`, вход по учётным записям (движок «По
учётной записи» и аудит конфигураций) — флаг `--allow-credentials`. Все действия CLI пишутся в журнал аудита от имени
`--actor`.

## 15. Обслуживание

```bash
docker compose ps                         # состояние
docker compose logs -f app                # логи API и движков
docker compose restart app                # перезапуск API
docker compose down                       # остановить (данные в томе pg_data сохраняются)

# обновление до свежей версии
git pull
docker compose up --build -d              # пересобрать образы; миграции применятся сами

# резервная копия БД
docker compose exec -T db pg_dump -U scanner scanner | gzip > scanner-$(date +%F).sql.gz

# полный сброс (УДАЛЯЕТ все прогоны, пользователей и справочники)
docker compose down -v && rm -f data/.bdu_loaded
```

**Нужно ли пересоздавать контейнеры при обновлении.** Да — после `git pull`
запускайте именно `docker compose up --build -d`, а не просто
`docker compose restart app`. Причины: новые функции могут добавлять
зависимости Python (они устанавливаются в образ `app` при сборке), а
веб-интерфейс компилируется и «запекается» в образ `web` — перезапуск его не
обновит. При `up --build` Docker пересоберёт изменившиеся образы и пересоздаст
контейнеры; данные (том `pg_data`), справочники и настройки сохраняются, если
не передавать `-v`. Новые миграции схемы БД применяются автоматически при
старте `app` (entrypoint делает `alembic upgrade head`), новые переменные из
`.env.example` при необходимости перенесите в свой `.env`. Простой
`restart app` достаточен только для точечной правки Python-кода без новых
зависимостей и без изменений веб-интерфейса (код `app` примонтирован как
`./:/app`).

Рекомендации для боевой установки:

- Наружу публикуется только веб (8080 или `SCANNER_WEB_PORT`); лучше
  поставить перед ним HTTPS-прокси. API и БД слушают только `127.0.0.1`
  хоста.
- `NET_RAW`/`NET_ADMIN` у контейнера `app` нужны nmap для SYN-сканирования и
  определения ОС.
- Журнал аудита только дописывается (append-only на уровне БД); просматривать
  его — раздел «Журнал аудита».

## 16. Известные ограничения

Честно о том, что в текущей версии ещё не доведено до конца:

- **Аудит учётных данных (`cred_audit`) пока нельзя настроить из веба или
  CLI.** Модуль готов (контролируемый перебор с лимитами), но наборы для
  проверки ему не передаются: прогон завершается без его находок, в журнале
  аудита — `cred_audit_skip` с результатом `no_credentials`. Это безопасное
  поведение по умолчанию; наборы проверки — следующая доработка. Аудит
  конфигураций уже работает на учётных записях договора (раздел 10).
- **Поиск по учётной записи сравнивает версии апстрима.** Бэкпорты
  исправлений в дистрибутивах (Debian, Ubuntu, RHEL, Astra) по версии не
  видны, поэтому часть находок по пакетам может быть уже закрыта — каждая
  такая находка помечена. Фильтрации по бюллетеням дистрибутивов (OVAL,
  security tracker) пока нет. Ядро по версии не сопоставляется.
- Без учётной записи дистрибутив Linux определяется только по баннерам
  сервисов: Astra Linux и РЕД ОС так обычно видны как «Linux» или Debian
  (см. «ОС хостов» в разделе 11). Хосты, просканированные до обновления, в
  группах появятся с ОС из прежних данных nmap; точнее — после нового прогона.
- Поиск по учётной записи работает только с Linux по SSH (dpkg, rpm, apk).
  Windows (WinRM) и сетевое оборудование пока не поддерживаются.
- Контент SCAP Security Guide ставится в образ пакетами `ssg-debderived` и
  `ssg-nondebian`, если они есть в репозитории базового образа; набор версий
  ОС зависит от версии пакета. Для Astra Linux, РЕД ОС и Альт контента SSG
  нет — на них аудит конфигураций выполняет только Lynis. Требования ФСТЭК
  можно проверять своим datastream (`SCANNER_CONFIG_AUDIT_SCAP_CONTENT`).
- На целях аудита конфигураций нужны: вход по SSH (пароль или ключ), права
  root через `sudo` (для ключа — NOPASSWD) и, для OpenSCAP, пакет
  `openscap-scanner`; без него проверяет только Lynis. Включённая подсистема
  `sftp` в sshd — через неё на хост передаётся контент проверки.
- Сборка Docker-образа (в том числе загрузка Nuclei) проверена только в CI
  на тестах; первая сборка на вашей машине — это и есть её проверка
  (см. [`TESTING.md`](TESTING.md), шаг 1).

## 17. Если что-то пошло не так

| Симптом | Что проверить |
|---|---|
| `app` перезапускается, в логах ошибка подключения к БД | `POSTGRES_PASSWORD` менялся после первого старта: том `pg_data` хранит старый пароль. Верните старый или `docker compose down -v` (данные удалятся) |
| В веб не пускает админа | Админ создаётся только при пустой БД; проверьте логин/пароль в `.env` на момент первого старта. Пароль короче 12 символов не принимается |
| После перезапуска «выкидывает» на вход | не задан `SCANNER_API_SECRET` — ключ генерируется заново при каждом старте |
| 5 неудачных входов подряд — вход заблокирован | подождите 15 минут (защита от перебора) |
| Находки без БДУ | БДУ не загружена: см. раздел 7; проверьте `ls data/.bdu_loaded` и логи загрузки |
| Прогон отклонён: «no requested target is in the engagement allowlist» | цели нет в allowlist выбранного договора |
| `vuln` не находит ничего или ошибка `no templates provided for scan` | шаблоны Nuclei не скачались (в логах `app` будет «шаблонов Nuclei нет»): `docker compose exec app nuclei -update-templates`. Нужен доступ контейнера к github.com |
| Ошибка сборки на шаге Nuclei | нет доступа к github.com при сборке; проверьте прокси/сеть сервера |
| `port is already allocated` / `address already in use` | порт хоста занят: задайте свободный в `.env` (`SCANNER_WEB_PORT` / `SCANNER_API_PORT` / `SCANNER_DB_PORT`), раздел 5.1 |
| Подробности ошибки модуля | раздел «Журнал аудита», действие `scan_finish`, или `docker compose logs app` |
