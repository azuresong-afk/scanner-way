# Архитектура сканера уязвимостей (рабочее название — «Scanner»)

> Назначение: инструмент для **авторизованного** security-тестирования по договору
> с заказчиком (pentest-by-contract). Сканируются только сети, к которым заказчик
> явно предоставил сетевой доступ и которые внесены в allowlist. Все действия
> сканера логируются. Это аналог по функциям «Сканер-ВС» / XSpider Pro, собранный
> из проверенных open-source движков с единым оркестратором, хранилищем и отчётами.

Версия документа: 0.1 (черновик для ревью) · Дата: 2026-10-28

---

## 1. Цели и границы

Пять функциональных модулей (из ТЗ):

1. **Исследование сети и инвентаризация** — обнаружение хостов, портов, сервисов,
   версий, fingerprint ОС.
2. **Поиск уязвимостей** — сопоставление найденных сервисов/версий с базами
   уязвимостей: NVD (CVE) **и** БДУ ФСТЭК России.
3. **Аудит конфигураций** — проверка хостов на соответствие бенчмаркам (CIS,
   требования ФСТЭК/ГОСТ).
4. **Аудит учётных данных** — контролируемая проверка слабых/дефолтных паролей на
   авторизованных хостах (с rate limiting и защитой от блокировок).
5. **Отчёты и сравнение прогресса** — хранение прогонов в PostgreSQL, сравнение по
   модулям раздельно и сводно, метрики тренда (открыто/закрыто/новое/регресс).

Плюс сквозные подсистемы: **роли и разграничение доступа (RBAC)** и **аудит
действий самого сканера**.

**Масштаб:** десятки–сотни хостов за прогон. **Платформа:** Linux, запуск через
Docker Compose.

### Что НЕ входит (явно)
- Эксплуатация уязвимостей / получение доступа (сканер только детектирует).
- Сканирование любых целей вне allowlist — технически блокируется на уровне ядра.

## 2. Выбор языка — Python (обоснование)

Основной язык — **Python 3.12**. Обоснование:

- Все целевые движки (nmap, Nuclei, OpenVAS/GVM, OpenSCAP, Lynis) — это внешние
  процессы или имеют Python-обвязку; оркестрация сводится к запуску процессов,
  парсингу XML/JSON и работе с БД — зона силы Python.
- Богатая экосистема: `python-libnmap`/`python-nmap` для разбора вывода nmap,
  `asyncio` для параллельного опроса десятков-сотен хостов, SQLAlchemy +
  Alembic для Postgres и миграций, FastAPI для API/веб-слоя, Jinja2 +
  WeasyPrint для HTML→PDF, `python-docx` для Word.
- Скорость сканирования определяется внешними движками и сетью, а не языком, —
  накладные расходы Python несущественны.
- Быстрая разработка и читаемость каркаса для последующего ревью и передачи.

Производительные «горячие» участки (если появятся) можно вынести в отдельные
воркеры; критичных для CPU участков в этой архитектуре нет — узкое место сеть и
внешние движки.

## 3. Компоненты и поток данных

```
                         ┌──────────────────────────────┐
                         │   Веб / API (FastAPI)         │
                         │   RBAC, запуск прогонов,      │
                         │   просмотр отчётов            │
                         └───────────────┬──────────────┘
                                         │
                    ┌────────────────────▼─────────────────────┐
                    │          Оркестратор прогона              │
                    │  allowlist-gate → план → очередь задач    │
                    │  rate-limit, аудит действий               │
                    └───┬──────┬──────┬──────┬──────────────────┘
                        │      │      │      │
           ┌────────────▼┐ ┌───▼───┐ ┌▼─────┐ ┌▼──────────┐
           │ discovery   │ │ vuln  │ │config│ │ cred_audit│   ← модули
           │ (nmap)      │ │(Nuclei│ │audit │ │(контрол.) │     (общий
           │ inventory   │ │ /GVM) │ │(SCAP/│ │           │      интерфейс
           └──────┬──────┘ └───┬───┘ │Lynis)│ └─────┬─────┘      ScanModule)
                  │            │     └──┬───┘       │
                  │            │        │           │
                  └────────────┴────┬───┴───────────┘
                                    │ нормализованные Finding
                           ┌────────▼─────────┐
                           │   PostgreSQL      │◄── feeds: NVD + БДУ ФСТЭК
                           │  (прогоны,        │     (периодическая загрузка
                           │   находки,        │      в справочники)
                           │   справочники)    │
                           └────────┬──────────┘
                                    │
                           ┌────────▼─────────┐
                           │   Reporting       │
                           │ diff (тренды) +   │
                           │ render HTML/PDF/  │
                           │ DOCX/JSON         │
                           └───────────────────┘
```

**Поток данных одного прогона:**
1. Пользователь (с ролью, допускающей запуск) создаёт прогон: цели + выбранные
   модули + профиль интенсивности.
2. Оркестратор проверяет каждую цель по **allowlist** (жёсткий гейт — всё, чего
   нет в allowlist, отбрасывается и логируется как отказ).
3. Для каждого модуля формируются задачи, исполняются с учётом **rate limit** и
   параллелизма; каждое внешнее действие пишется в журнал аудита.
4. Модули возвращают сырой вывод движка → нормализатор превращает его в единую
   запись `Finding` (хост, порт, сервис, версия, идентификатор уязвимости,
   severity, ссылки на NVD/БДУ).
5. Находки сохраняются в Postgres с привязкой к `scan_run`.
6. Reporting строит отчёт и сравнение с предыдущим прогоном.

## 4. Выбор движков, лицензии, роль в системе

| Модуль | Движок (кандидат) | Лицензия | Роль |
|---|---|---|---|
| Discovery / inventory | **nmap** (+ NSE) | NPSL (на базе GPLv2, с оговорками) | Хосты, порты, сервисы, версии, fingerprint ОС (`-sV -O`) |
| Vuln detection | **Nuclei** (ProjectDiscovery) | MIT | Шаблонные проверки по сервисам/веб; быстрый, расширяемый |
| Vuln detection (глубоко) | **OpenVAS / Greenbone (GVM)** | GPLv2 | Классический сетевой сканер с большой базой NVT; тяжёлый, опционально |
| Config audit | **OpenSCAP** | LGPLv2.1+ | SCAP/XCCDF/OVAL, профили CIS и готовые бенчмарки |
| Config audit (лёгкий) | **Lynis** | GPLv3 | Хостовый аудит Linux/Unix, быстрый, скриптуемый |
| Cred audit | собственный контролируемый модуль (см. §7) | — | Проверка слабых/дефолтных учёток по согласованию |

**Лицензионное замечание (важно для коммерческого использования):**
- Nmap под **NPSL** — распространение/встраивание в коммерческий продукт имеет
  ограничения; безопаснее вызывать nmap как внешний инструмент, установленный в
  окружении заказчика/контейнере, а не линковать/перепродавать. Нужна проверка
  юристом для продуктовой поставки.
- GPL-движки (OpenVAS, Lynis) — при вызове как отдельных процессов (а не линковки)
  copyleft на наш код не распространяется, но поставку надо оформлять аккуратно.
- MIT (Nuclei) и LGPL (OpenSCAP) — наиболее свободны для интеграции.

Стратегия: **все движки — это сменные бэкенды за общим интерфейсом `ScanModule`**.
Старт делаем на nmap + Nuclei + OpenSCAP/Lynis (лёгкие, MIT/LGPL/быстрые),
OpenVAS подключаем как опциональный тяжёлый бэкенд позже.

## 5. Интеграция баз уязвимостей (NVD + БДУ ФСТЭК)

Две независимые загрузки в локальные справочники Postgres, плюс слой сопоставления.

### NVD (CVE)
- Источник: NVD JSON feeds / NVD API 2.0.
- Загружаем CVE с CVSS (v3.1/v4), CPE-конфигурациями, ссылками.
- Сопоставление: сервис+версия → CPE → список CVE.

### БДУ ФСТЭК России
- Источник: официальная выгрузка БДУ (банк данных угроз, `bdu.fstec.ru`).
  **Формат подтверждён по образцу заказчика (`vullist.xlsx`): это XLSX**
  (~98 600 записей на момент выгрузки). Загружаем периодически.
- Раскладка файла: лист **«Уязвимости»**; строки 1–2 — групповые заголовки,
  **строка 3 — имена колонок**, данные с 4-й строки. 32 колонки.
- Ключевые колонки: `Идентификатор` (`BDU:ГГГГ-NNNNN`), `Наименование`,
  `Описание`, `Вендор ПО`, `Название ПО`, `Версия ПО`, `Тип ПО`,
  `Класс уязвимости`, `CVSS 2.0/3.0/4.0`, `Уровень опасности` (текст с базовой
  оценкой — число после слова «составляет»), `Возможные меры по устранению`,
  `Статус`, `Наличие эксплойта`, `Тип ошибки CWE`, `Ссылки на источники`,
  **`Идентификаторы других систем описаний уязвимости`** — строка вида
  `CVE-2013-5946, OSVDB ID:100840, ...`, откуда регуляркой извлекаются CVE
  (ключ кросс-ссылки с NVD).
- Парсер (`scanner/feeds/bdu_fstec.py`) маппит колонки **по именам** из строки
  заголовка, поэтому устойчив к перестановке колонок в новых выгрузках. Реализован
  и провалидирован на реальном файле (1964 из 2000 первых записей имеют CVE,
  оценки 1.2–10.0). Нормализуем в `reference_bdu_entry`; где есть CVE — строим
  связь `reference_bdu_entry ↔ reference_nvd_cve` по CVE-идентификатору.

### Слой сопоставления
Находка модуля несёт либо CVE (от Nuclei/OpenVAS), либо сервис+версию. Движок
сопоставления обогащает находку:
- CVE → подтягиваем запись NVD и, если есть связь, запись БДУ ФСТЭК;
- сервис+версия → CPE → CVE → далее как выше.

Так каждая находка в отчёте показывает **и CVE/NVD, и идентификатор БДУ ФСТЭК**,
что требуется для гос-контекста.

> Формат выгрузки БДУ зафиксирован по файлу заказчика (XLSX) — см. выше.

## 6. Схема БД (ER, PostgreSQL)

Полная DDL — в [`db/migrations/0001_initial.sql`](../db/migrations/0001_initial.sql).
Логическая модель:

```
users ──< user_roles >── roles ──< role_permissions >── permissions

targets_allowlist        ── разрешённые к сканированию CIDR/хосты (engagement-scope)
engagements              ── договор/проект заказчика; владеет allowlist и прогонами

scan_runs                ── один прогон: когда, кем, какие модули, профиль
  │
  ├──< host_results      ── на хост: статус, ОС-fingerprint
  │      │
  │      └──< service_results  ── порт/протокол/сервис/версия/продукт(CPE)
  │
  └──< findings          ── нормализованная находка (ядро отчётов)
         fields: engagement_id, scan_run_id, module, host, port,
                 finding_type(vuln|config|cred|info),
                 vuln_id (CVE или BDU), title, severity, cvss,
                 evidence, status(open|fixed|...), first_seen_run, last_seen_run,
                 dedup_key  ← стабильный ключ (hash(host+port+vuln_id+module))

reference_nvd_cve        ── справочник NVD (cve_id, cvss, cpe[], refs)
reference_bdu_entry      ── справочник БДУ ФСТЭК (bdu_id, cve_ids[], severity, ...)

audit_log                ── действия сканера и пользователей (кто/что/когда/цель)
```

**Ключ сравнения прогресса (`dedup_key`)** строится по `(host, port, vuln_id,
module)` — именно он позволяет считать тренды: та же находка в новом прогоне =
«ещё открыта»; исчезла = «закрыта»; появилась новая = «новое»; была закрыта и
вернулась = «регресс». См. §8.

## 7. Модель безопасности (ключевое для авторизованного тестирования)

Три обязательных механизма, встроенных в **ядро**, а не в отдельные модули:

### 7.1 Allowlist-гейт (жёсткий)
- Каждый прогон привязан к `engagement`; у engagement есть список разрешённых
  целей (CIDR/IP/hostname), заполняемый по договору.
- Перед **любым** сетевым действием оркестратор проверяет цель по allowlist.
  Нет в allowlist → действие не выполняется, пишется отказ в `audit_log`.
- Проверка централизована (`core/allowlist.py`), модули не умеют обходить её —
  они получают уже отфильтрованный список целей.

### 7.2 Rate limiting и защита от DoS/блокировок
- Глобальные и по-хостовые лимиты: запросов/сек, одновременных соединений,
  пауза между попытками.
- Для cred audit — отдельные жёсткие лимиты: малое число попыток на учётку/хост,
  экспоненциальная пауза, стоп при признаках блокировки аккаунта. Цель — не
  вызвать блокировки и не создать DoS, а лишь выявить **очевидно слабые/дефолтные**
  учётки, как это делают OpenVAS/Nessus в режиме credential check.
- Профили интенсивности («щадящий/обычный/агрессивный») задаются на прогон.

### 7.3 Аудит действий
- Каждое внешнее действие (команда движку, сетевой запрос к цели, попытка
  аутентификации) и каждое действие пользователя (запуск/остановка/экспорт)
  пишется в `audit_log` с временем, субъектом, целью и результатом.
- Журнал неизменяемый на уровне приложения (только append), для разбора инцидентов.

### 7.4 Про cred audit отдельно
Модуль проверки учётных данных включается **только** явно и только по
согласованию с заказчиком, работает исключительно по allowlist-хостам, с
лимитами из §7.2. Реализуется как управляемый модуль-обёртка; в каркасе это
интерфейс и заглушка с жёсткими лимитами по умолчанию, без встроенных словарей
атак — словарь/набор дефолтных учёток подключается оператором осознанно.

## 8. Отчёты и сравнение прогресса

**Хранение:** все находки всех прогонов остаются в Postgres (не перезаписываются).

**Сравнение (diff) считается по `dedup_key` между двумя прогонами:**
- `open` — есть в обоих;
- `fixed` — была в предыдущем, нет в текущем;
- `new` — нет в предыдущем, есть в текущем;
- `regression` — была `fixed` в более раннем, снова появилась.

**Разрезы отчётов (из требований):**
- **По каждому модулю раздельно** (discovery / vuln / config / cred).
- **Сводный отчёт по всем модулям** за прогон.
- **Тренд между прогонами** с метриками open/fixed/new/regression и динамикой по
  severity.

**Форматы вывода:**
- **HTML** (Jinja2) — основной, интерактивный.
- **PDF** (WeasyPrint из HTML) — для передачи заказчику.
- **Word .docx** (`python-docx`) — для редактируемых отчётов.
- **JSON** — для интеграций (SIEM/GRC и т.п.).

## 9. Роли и разграничение доступа (RBAC)

Базовый набор ролей (уточним при ревью):
- **admin** — пользователи, роли, engagements, allowlist.
- **operator** — запуск/остановка прогонов, просмотр.
- **auditor/viewer** — только просмотр и экспорт отчётов.
- Разрешение на **cred audit** — отдельный флаг-право, не входит в operator по
  умолчанию.

Модель: `users ──< user_roles >── roles ──< role_permissions >── permissions`.
Проверка прав — на уровне API до постановки задач.

## Решения по уточнениям заказчика (закрыто)
1. **Формат выгрузки БДУ ФСТЭК — XLSX** (образец `vullist.xlsx`). Парсер
   реализован под реальную схему (см. §5).
2. **Аудит конфигураций — только безагентный** (см. §4.1). Постоянная установка
   агентов на цели не предполагается.
3. Репозиторий `azuresong-afk/scanner-way` создан и подключён.

### 4.1 Безагентный аудит конфигураций
Аудит выполняется **по SSH без установки постоянного агента** на целевой хост:
- **OpenSCAP** — через `oscap-ssh`: движок остаётся на машине сканера, по SSH
  на цели выполняется сбор (oscap) по профилю XCCDF/OVAL, результат возвращается
  на сканер. Профили: CIS и, для гос-контекста, профили под требования
  ФСТЭК/ГОСТ.
- **Lynis** — запуск в режиме удалённого аудита: бинарь доставляется по SSH во
  временный каталог, выполняется, отчёт забирается, временные файлы удаляются
  (без постоянного агента).
- Требуются учётные данные/ключ SSH с правами аудита на целевых хостах (в рамках
  engagement); все подключения и команды пишутся в журнал аудита.
