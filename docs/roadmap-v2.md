# Дорожная карта v2: до уровня коммерческих сканеров

Первая дорожная карта (`docs/roadmap.md`, задачи T1–T8) выполнена: в `main` есть
обнаружение (nmap), поиск уязвимостей (Nuclei и по учётной записи SSH), привязка к
БДУ ФСТЭК и NVD, отчёты HTML/PDF/DOCX/JSON со сравнением прогонов, API с ролями,
веб-интерфейс, расписания и установка одной командой.

Этот документ описывает **следующий этап**: закрыть разрывы с коммерческими
решениями (Сканер-ВС, XSpider / MaxPatrol, Nessus). Формат тот же, что у первой
карты: задачи разбиты так, чтобы их можно было вести **в параллельных тредах**,
каждая задача владеет своими файлами и оформляется отдельным PR в `main`. Для
каждой задачи дан самодостаточный промт и выбрана модель с обоснованием.

**Приоритет №1:** аудит конфигураций и аудит паролей должны использовать
сохранённые учётные записи договора (задачи **R1a** и **R1b**). Сейчас оба модуля
пишут в журнал `no_credentials` и ничего не проверяют.

**Сквозные требования заказчика (действуют для всех задач):**

- Привязка находок к **БДУ ФСТЭК** остаётся главной функцией: всё новое (бюллетени
  дистрибутивов, Windows KB, профили соответствия, приоритизация) должно сохранять
  и показывать `BDU:…` рядом с CVE.
- Итог любой проверки — **понятный отчёт с рекомендациями по устранению** и
  ссылками на бюллетени вендора / БДУ / NVD / CWE (без эксплойтов, новостей и
  агрегаторов).
- **Сроки устранения не назначать** ни в отчётах, ни в интерфейсе (в JSON поле для
  интеграций остаётся пустым). Это касается и приоритизации R6: она даёт порядок
  «что исправлять первым», а не дедлайны.
- Разбивка по хостам обязательна; отчёт по умолчанию — по одному прогону,
  сравнение — только по явной опции «Сравнить с».
- Безопасность: только цели из allowlist, rate limiting, запись действий в аудит,
  секреты только в зашифрованном хранилище (`CredentialVault`), в журнал и
  находки не попадают.

- R9 шлёт события «новые критичные» по ранжированию R6 и маршрутизирует по

## 4. Правила координации

### 4.1. Номера миграций (обязательно)

Раньше параллельные PR сталкивались номерами миграций. Поэтому **номера
зарезервированы заранее** и цепочка линейная:

| Номер | Файл | Задача | Волна | `down_revision` |
|-------|------|--------|-------|-----------------|
| 0008 | `0008_credential_become.py` | R1a | 1 | `0007` |
| 0009 | `0009_cred_audit_sets.py` | R1b | 1 | `0008` |
| 0010 | `0010_assets.py` | R7 | 1 | `0009` |
| 0011 | `0011_feed_sync.py` | R12 | 1 | `0010` |
| 0012 | `0012_distro_advisories.py` | R2 | 2 | `0011` |
| 0013 | `0013_risk_scoring.py` | R6 | 2 | `0012` |
| 0014 | `0014_windows_credentials.py` | R3 | 2 | `0013` |
| 0015 | `0015_compliance.py` | R5 | 3 | `0014` |
| 0016 | `0016_notifications.py` | R9 | 3 | `0015` |
| 0017–0019 | — | резерв на исправления после интеграции I1–I3 | — | следующий свободный |

Правила:

1. Задача использует **только свой номер**. Нужна вторая миграция — это второй
   файл в той же задаче с суффиксом `b` нельзя; вместо этого всё изменение схемы
   задачи помещается в одну миграцию.
2. `revision = "00NN"`, `down_revision` — номер из таблицы, имя файла начинается
   с того же номера. Существующие миграции **не редактируются**.
3. **Мёрж PR с миграциями — строго по возрастанию номера** внутри волны. PR без
   миграций (I1–I3, R0) мёржатся в любой момент. Если PR с бóльшим номером готов
   раньше — он ждёт; его тесты при этом гоняются локально на ветке, где
   предшествующие миграции временно заглушены пустыми ревизиями (заглушки в PR
   не попадают).
4. Если заказчик хочет смёржить вне очереди — обе задачи **меняются номерами**
   (переименовать файлы, `revision`, `down_revision`, ссылки в docstring), а
   таблица выше правится в том же PR.
5. Изменения схемы — только аддитивные: новые таблицы, `ADD COLUMN` с `NULL` или
   `DEFAULT`, новые индексы. Никаких `DROP`/`RENAME` существующих колонок в этом
   этапе. `downgrade()` обязателен.
6. Модели SQLAlchemy в `scanner/core/db.py` дописываются **в конец своего
   раздела** (или в новый файл модуля задачи), существующие классы меняются
   только добавлением полей.
7. Тест R0 (`tests/test_migration_chain.py`) в CI проверяет: одна голова, номера
   идут подряд, `revision` совпадает с префиксом файла. Нарушение — красный CI.

**Обоснование моделей по задачам:**

- **R0 — Haiku 5.5.** Один тест на 40 строк с точной спецификацией; рассуждать
  не о чем, важна скорость.
- **R1a — Opus 5.5.** Перенос транспорта аудита с системного `ssh` на paramiko,
  `sudo` с паролем без утечки в argv/журнал, выбор учётки по области действия,
  передача архива Lynis без stdin-конфликта. Ошибка = утечка секрета или
  повисший root-процесс на хосте заказчика.
- **R1b — Opus 5.5.** Реальные проверки паролей по сети на чужих хостах: лимиты,
  анти-lockout, отсутствие встроенных словарей, корректная классификация ответов
  протоколов (неверный пароль ≠ блокировка ≠ ошибка сети). Плюс чтение
  `/etc/shadow` без выноса хешей с хоста. Это самый чувствительный модуль.
- **R7 — Sonnet 5.5.** Классический CRUD + фильтры + UI; логика простая.
- **R12 — Sonnet 5.5.** Планировщик по готовому образцу (`api/scheduler.py`) и
  вызов уже написанных загрузчиков; основная работа — надёжность и интерфейс
  статуса.
- **R2 — Opus 5.5.** Сердце точности: сравнение версий dpkg/rpm по правилам
  менеджеров, разбор OVAL/трекеров пяти семейств, решение «уязвим / закрыто
  бэкпортом / нет данных» без потери привязки к БДУ. Ошибка = пропущенная
  уязвимость или ложное «исправлено».
- **R6 — Sonnet 5.5.** Загрузчики EPSS/KEV — простые CSV/JSON; формула риска
  прозрачная и задана в промте. Логика не требует глубокого анализа, нужна
  аккуратность в отчёте и UI.
- **R3 — Opus 5.5.** Новый протокол доступа (NTLM/Kerberos/TLS), сопоставление
  KB ↔ CVE с учётом замещения обновлений (supersedence), чтение реестра и
  политик. Сложная логика сопоставления и безопасность учёток.
- **R5 — Opus 5.5.** Предметно сложное соответствие мер приказов ФСТЭК (ИАФ, УПД,
  РСБ, ЗИС, АНЗ, ОПС…) техническим проверкам с учётом класса/уровня защищённости;
  ошибка в маппинге = неверный процент соответствия в документе для заказчика.
- **R9 — Sonnet 5.5.** Интеграции по документированным протоколам (SMTP, Telegram
  Bot API, RFC 5424/CEF, Jira REST) + очередь повторов + UI.
- **I1–I3 — Sonnet 5.5.** Сквозные тесты и документация по готовому коду.
