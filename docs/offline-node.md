# Автономный узел-сканер (закрытый сегмент без связи с центром)

Автономный узел нужен там, где в сегмент нельзя провести даже одно исходящее
правило на межсетевом экране: АСУ ТП, закрытый контур, изолированная площадка.
Связи между центром и узлом нет совсем. Задание и результат переносятся
файлами на носителе, как в MaxPatrol и RedCheck для закрытых контуров.

Если одно исходящее правило «узел → центр, TCP 443» допустимо, проще сетевой
режим (узел сам забирает задания и отдаёт результат), см. раздел о
распределённых сканерах в [INSTALL.md](INSTALL.md).

## Как это устроено

```
   ЦЕНТР (веб + API + PostgreSQL)                  ЗАКРЫТЫЙ СЕГМЕНТ
  ┌──────────────────────────────┐               ┌──────────────────────────────┐
  │ «Новый прогон» → узел        │               │ автономный узел (Linux +     │
  │ «Выгрузить задание»          │  job.scnjob   │ Docker, без API и без БД     │
  │   подпись ключом центра,     │ ───носитель──▶│ сервера)                     │
  │   цели и учётки зашифрованы  │               │ scanner node run-job         │
  │   на ключ узла               │               │   проверка подписи, срока,   │
  │                              │ result.scnres │   allowlist узла; скан;      │
  │ «Загрузить результат»        │ ◀──носитель── │   результат подписан узлом и │
  │   подпись узла, привязка к   │               │   зашифрован на ключ центра  │
  │   заданию, allowlist договора│               │                              │
  │ → отчёты, «Активы»,          │               │ справочники БДУ/NVD: свой    │
  │   «Что исправить»            │               │ SQLite, комплект данных      │
  └──────────────────────────────┘               └──────────────────────────────┘
          сетевой связи нет ни в одну сторону — только носитель
```

**Связность.**

| Откуда → куда | Что нужно |
|---|---|
| Центр ↔ узел | ничего: ни входящих, ни исходящих правил |
| Узел → интернет | не нужен: бюллетени ОС и шаблоны Nuclei приходят в комплекте данных |
| Узел → хосты сегмента | порты проверок, как при обычном прогоне: ICMP и TCP/UDP сканирования nmap, SSH 22, WinRM 5986, SNMP 161/UDP, порты СУБД (5432, 3306, 1433, 1521) — только для модулей, выбранных в прогоне. Трафик не выходит за пределы сегмента |

**Ключи.** У центра и у каждого узла по две пары ключей: Ed25519 (подпись) и
X25519 (шифрование для получателя, AES-256-GCM). Открытыми ключами стороны
обмениваются один раз при установке, тоже на носителе, и сверяют отпечатки
(`ab12-cd34-…`) по телефону или по акту. Закрытый ключ узла никогда не покидает
узел; ключ центра выводится из секрета центра (`SCANNER_OFFLINE_KEY`, иначе
`SCANNER_CREDENTIALS_KEY` / `SCANNER_API_SECRET`) и нигде не хранится.

**Что защищено на носителе.**

| Угроза | Что происходит |
|---|---|
| Носитель потерян или скопирован | Цели, учётные записи и находки зашифрованы: задание читает только узел, результат — только центр. В открытом заголовке только номера, имя узла, сроки и счётчики |
| Задание изменено или подделано | Узел проверяет подпись центра по закреплённому `center.pub` и отклоняет файл до расшифровки |
| Задание выпущено для другого узла | Отклоняется: в задании отпечаток ключа узла-получателя |
| Старое задание запущено снова | Отклоняется по журналу узла (`journal.jsonl`) и по сроку действия (по умолчанию 14 дней) |
| Результат изменён, подделан, от другого задания или загружен второй раз | Центр отклоняет: подпись узла, id и SHA-256 файла задания, статус задания |
| В результате адреса вне договора | Результат отклоняется целиком |
| Центр скомпрометирован и выпустил задание на чужие сети | Узел сканирует только пересечение целей задания со своим allowlist (`--scope` при установке) |

## Установка

### 1. В центре: завести узел

1. «Сканеры» → «Добавить узел», тип **«Автономный»**. Имя (например
   `АСУ-ТП-1`) и сети сегмента, которые узлу разрешено сканировать.
2. «Сканеры» → «Ключ центра» → **«Скачать center.pub»**. Запишите отпечаток.

Ключ центра можно получить и из командной строки на сервере центра:

```sh
docker compose exec app scanner --no-migrate offline center-key --out /data/center.pub
```

### 2. Собрать носитель для установки

На машине со связью (обычно это сервер центра):

```sh
docker save scanner:latest -o scanner-image.tar           # образ сканера
docker compose exec app scanner bundle export \
    --out /data/bundle/scanner-data-$(date +%Y%m%d).tar   # справочники
```

На носитель: `scanner-image.tar`, `scanner-data-<дата>.tar`,
`docker-compose.node-offline.yml` из репозитория, `center.pub`.

### 3. На узле: установить

Требования: Linux, Docker с плагином compose, 2 ядра, 4 ГБ ОЗУ, 10 ГБ диска.
Сетевая карта в сегменте; интернет не нужен.

```sh
mkdir -p /opt/scanner-node/media && cd /opt/scanner-node
cp /mnt/usb/docker-compose.node-offline.yml .
cp /mnt/usb/center.pub /mnt/usb/scanner-data-*.tar media/
docker load -i /mnt/usb/scanner-image.tar

# короткая команда для разовых контейнеров узла
alias snode='docker compose -f /opt/scanner-node/docker-compose.node-offline.yml run --rm node'

snode node init --name "АСУ-ТП-1" --scope 10.10.0.0/16 \
    --center-key /media/center.pub --pub-out /media/node.pub
snode bundle import /media/scanner-data-20261106.tar
```

Каталог `/opt/scanner-node/media` виден в контейнере как `/media`: туда
кладутся задания и пишутся результаты (другой каталог — переменная
`SCANNER_MEDIA_DIR`).

`node init` печатает два отпечатка:

* **ключ центра** — сверьте с тем, что показан в центре («Ключ центра»);
* **ключ узла** — его сверят в центре при загрузке ключа узла.

`--scope` — собственный allowlist узла. Узел не будет сканировать ничего вне
этих сетей, даже по подписанному заданию.

Открытый ключ узла записан в `media/node.pub` — перенесите его на носитель.
Закрытый ключ остаётся в томе узла и с узла не выносится.

### 4. В центре: загрузить ключ узла

«Сканеры» → узел → **«Ключ узла»** → загрузить `node.pub`. Отпечаток в центре
должен совпасть с тем, что напечатал `node init`. После этого узел готов.

## Прогон на автономном узле

1. **Центр.** «Прогоны» → «Новый прогон» → «Где выполнять» → автономный узел.
   Модули, цели и учётки — как обычно. Прогон встаёт в очередь.
2. **Центр.** В карточке прогона **«Выгрузить задание»** (срок действия по
   умолчанию 14 дней). Скачивается `job-<узел>-run<N>-<дата>.scnjob`, прогон
   переходит в «Выполняется» и ждёт результат. Потерян файл — «Скачать
   задание ещё раз» (тот же файл).
3. **Носитель → узел.** Проверить задание, не запуская:
   ```sh
   snode node inspect /media/job-АСУ-ТП-1-run42-20261106-1200.scnjob
   ```
4. **Узел.** Выполнить:
   ```sh
   snode node run-job /media/job-АСУ-ТП-1-run42-20261106-1200.scnjob --out /media \
       --confirm-authorized
   ```
   Перед запуском узел проверяет, что справочники БДУ/NVD загружены: без них
   результат был бы ложно чистым, и задание не запустится. Результат —
   `/media/result-<узел>-run<N>-<дата>.scnres`.
5. **Носитель → центр.** В карточке прогона или в «Сканеры» → **«Загрузить
   результат»**. Центр проверяет подпись и привязку к заданию, сохраняет
   находки, сравнивает с прошлым прогоном, обновляет «Активы» и «Что
   исправить», шлёт уведомления. В журнале аудита центра появятся и действия
   узла по заданию (субъект `node:<имя>`).

Если результат не загружен за срок задания + 3 дня, прогон завершается
ошибкой «Результат с автономного узла не загружен в срок». Ненужное задание
отменяется кнопкой «Отменить задание»: результат по нему больше не примется.

## Обслуживание узла

* **Справочники.** Узел сопоставляет находки со своей копией БДУ/NVD,
  бюллетеней ОС и шаблонов Nuclei. Обновлять тем же носителем: в центре
  `scanner bundle export`, на узле `snode bundle import <файл>`. Комплект
  накатывается поверх, с нуля ничего не грузится. Дата справочников узла
  видна в центре рядом с загруженным результатом.
* **Новая версия сканера.** `docker load -i scanner-image.tar` с носителя;
  каталог узла (ключи, журнал, справочники) сохраняется в томе `node_home`.
* **Часы узла.** Срок действия задания проверяется по часам узла. Держите
  их хотя бы приблизительно верными.
* **Смена ключей узла.** `snode node init … --force` и снова загрузить
  `node.pub` в центр. Невыполненные задания по старому ключу перестанут
  приниматься, поэтому сначала загрузите или отмените их.
* **Смена секрета центра** (`SCANNER_OFFLINE_KEY`) меняет ключ центра: его
  нужно заново поставить на все автономные узлы (`node init --force` с новым
  `center.pub`). Чтобы смена `SCANNER_API_SECRET` не затрагивала узлы, задайте
  отдельный `SCANNER_OFFLINE_KEY` с самого начала.
* **Резервная копия узла** — том `node_home` (в нём закрытые ключи: храните
  копию так же, как ключи шифрования учёток центра).

## Команды узла

| Команда | Что делает |
|---|---|
| `scanner node init --name … --scope … --center-key center.pub [--pub-out node.pub] [--force]` | установка: ключи, allowlist, ключ центра |
| `scanner node show` | имя, сети, отпечатки, последние задания |
| `scanner node inspect <job.scnjob>` | проверить задание без запуска |
| `scanner node run-job <job.scnjob> --out <каталог> --confirm-authorized` | выполнить задание, записать результат |
| `scanner bundle import <scanner-data.tar>` | обновить справочники узла |
| `scanner offline center-key [--out center.pub]` | (в центре) открытый ключ центра |

API центра: `GET /offline/center-key`, `PUT /nodes/{id}/public-key`,
`POST /runs/{id}/offline/export`, `GET /runs/{id}/offline/job`,
`POST /runs/{id}/offline/cancel`, `POST /offline/results/preview`,
`POST /offline/results` (тело — файл `.scnres`), `GET /nodes/{id}/offline-jobs`.
