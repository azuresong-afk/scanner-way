# Чек-лист приёмочного тестирования

Что проверить после установки по [`INSTALL.md`](INSTALL.md), по шагам. В
каждом шаге: что сделать и какой результат ожидается. Отмечайте `[x]` по ходу;
если результат не совпал, запишите номер шага, что увидели и вывод
`docker compose logs app` за это время.

> Все прогоны — только по собственному стенду или по адресам из allowlist
> договора, на которые есть письменное разрешение.

## Подготовка

- Сервер с установленным сканером (INSTALL.md, разделы 1–5).
- Учебная цель, которая принадлежит вам, в отдельной сети с фиксированными
  адресами (INSTALL.md, раздел 10):

  ```bash
  docker network create --subnet 172.30.0.0/24 lab-net
  docker network connect lab-net "$(docker compose ps -q app)"
  docker run -d --name lab-web --network lab-net --ip 172.30.0.10 httpd:2.4.49
  docker exec lab-web sed -i '/<Directory \/>/,/<\/Directory>/ s/Require all denied/Require all granted/' \
      /usr/local/apache2/conf/httpd.conf
  docker restart lab-web
  ```

  Правка конфига делает CVE-2021-41773 эксплуатируемой (проверка — INSTALL.md,
  раздел 10, шаг 3).

  Ниже `LAB_IP` = `172.30.0.10` (вносится в allowlist), `OUT_IP` =
  `172.30.0.20` (в allowlist **не** вносится; контейнер по нему не нужен —
  сканер должен отказать раньше, чем пойдёт в сеть).
- Для шага 8а — вторая учебная цель `lab-ssh` (Debian с SSH,
  `172.30.0.11`); команды для неё — в самом шаге.
- Три учётки, которые вы заведёте на шаге 4: `admin`, `op1` (operator),
  `aud1` (auditor).

Если вы меняли порты в `.env` (INSTALL.md, раздел 5.1), подставляйте в
командах свои вместо 8080 и 8000.

Примерное время на весь чек-лист: 1–1,5 часа, из них большая часть — сборка и
загрузка справочников.

## Шаг 8. Модуль «Поиск уязвимостей» (Nuclei) и привязка к БДУ ★

Главная проверка продукта. Под `op1`: цель `LAB_IP`, модули «Обнаружение» +
«Поиск уязвимостей», профиль `normal` (10–15 минут; на `gentle` примерно
50 минут на одну цель — таймаут масштабируется от профиля и числа целей, см.
INSTALL.md, раздел 10). Если прогон обрывается по таймауту, уже найденное
сохраняется, а в находках появляется пометка «Поиск уязвимостей прерван по
таймауту» — повторите прогон на профиле выше.

| # | Действие | Ожидаемый результат |
|---|---|---|
| 8.1 | Запустить, дождаться `done` | Прогон завершён без ошибок модулей |
| 8.2 | «Находки», модуль «Уязвимости» | Много находок по Apache httpd 2.4.49 (несколько десятков) с разными уровнями опасности — критические, высокие, средние. Для непропатченной 2.4.49 это норма: сопоставление по версии выдаёт все уязвимости из диапазона затронутых версий, каждая — отдельной строкой со своим уровнем и своим БДУ |
| 8.3 | Найти `CVE-2021-41773` | Отдельная находка, уровень «Высокий», подтверждена Nuclei (обход каталога). В карточке: БДУ `BDU:2021-04903`, CVE, CVSS, доказательство, рекомендация, ссылки на БДУ ФСТЭК и NVD |
| 8.4 | Открыть находку, сопоставленную только по версии (шаблон Nuclei не срабатывал) | В доказательстве строка «Совпадение по версии из баннера: возможен бэкпорт исправления…»; у находки свой БДУ/CVE, CVSS и уровень опасности |
| 8.5 | Проверить детект-находки: «Apache Detection», «WAF Detection», «HTTP TRACE», «Allowed Options Method», «HTTP Missing Security Headers» | Остаются **информационными**, без привязанных CVE/БДУ и НЕ помечены критическими. Это регресс-проверка: раньше детекты ошибочно собирали на себя весь список CVE версии и становились critical |
| 8.6 | Перейти по ссылке на БДУ | Открывается страница этой уязвимости на bdu.fstec.ru |
| 8.7 | Фильтр «есть БДУ»; поиск по `BDU:2021` и по `CVE-2021-41773` | В фильтре остаются только находки с БДУ; CVE-2021-41773 находится обоими запросами |
| 8.8 | «Сводка» | Распределение по опасности, доля сопоставленных с БДУ > 0 %, хост в «самых уязвимых», уязвимость в «приоритетных» |
| 8.9 | Журнал аудита, действия `nuclei_exec` и `banner_match` | `nuclei_exec` — команда Nuclei с `-rate-limit`/`-concurrency`, без автообновления; `banner_match` — результат `ok` с числом находок по версии |

**Главный критерий приёмки привязки к БДУ — сопоставление по версии.** Оно
срабатывает всегда, когда discovery распознал продукт и версию, независимо от
того, сработал ли конкретный шаблон Nuclei. Поэтому «много находок» в 8.2 —
признак того, что привязка работает, а не ошибка.

Если находок нет или они без БДУ:
- находок вообще нет → не загружены шаблоны Nuclei (шаг 1.3) либо цель недоступна;
- есть находки, но ни у одной нет БДУ → не загружена выгрузка БДУ. Проверка:
  `docker compose exec db psql -U scanner -c "select count(*) from reference_bdu_entry"`
  должно быть > 0; если 0 — вернитесь к шагу 2;
- `CVE-2021-41773` не подтверждена Nuclei, но присутствует среди находок по
  версии → это нормально (цель могла быть уязвима не полностью); привязка к
  БДУ при этом всё равно проверяется по версии.

## Шаг 8а. Поиск уязвимостей по учётной записи (SSH) ★

Второй движок поиска уязвимостей: сканер входит на хост по SSH, читает список
установленных пакетов (dpkg/rpm/apk) и сопоставляет их версии с БДУ ФСТЭК и
CVE/NVD. Движок выбирается в форме запуска: «Nuclei», «По учётной записи»

## Шаг 9. Аудит конфигураций по учётной записи ★

Аудит конфигураций (CIS, требования ФСТЭК/ГОСТ) использует те же учётные

Аудит конфигураций (CIS, требования ФСТЭК/ГОСТ) использует те же учётные
записи договора, что и шаг 8а. Сканер входит на хост по SSH, повышает права
через `sudo`, передаёт на хост контент OpenSCAP и Lynis во временный каталог
по SFTP, запускает проверку и удаляет каталог. Пароль для `sudo` подаётся
скрыто, через stdin соединения, и нигде не сохраняется.

Подготовка — на учебной цели `lab-ssh` из шага 8а дать учётке `audit` sudo
по паролю и поставить движок OpenSCAP:

```bash
docker exec lab-ssh sh -c "apt-get install -y -qq sudo openscap-scanner >/dev/null \
   && echo 'audit ALL=(ALL) ALL' > /etc/sudoers.d/audit && chmod 440 /etc/sudoers.d/audit"
docker compose exec app ls /usr/share/xml/scap/ssg/content/ | grep debian
```

Последняя команда показывает, есть ли в образе сканера контент SCAP Security
Guide для Debian (`ssg-debian12-ds.xml`). Если строки нет, OpenSCAP не
запустится, а аудит выполнит только Lynis. Причину покажет находка-сводка.

## Шаг 9а. Аудит паролей по согласованному набору учёток ★

## Шаг 9б. Профили соответствия ФСТЭК №117/21/239 и CIS ★

Проверяем расчёт процента соответствия требованиям приказов ФСТЭК России №117
(ГИС, классы К1–К3), №21 (ИСПДн, УЗ1–УЗ4), №239 (значимые объекты КИИ,
категории 1–3) и CIS (CIS Controls v8 по группам внедрения IG1–IG3 и CIS
Benchmark по правилам OpenSCAP). Профили — данные в
`scanner/compliance/profiles/*.yaml`: каждая мера сопоставлена с техническими
проверками (правила OpenSCAP и тесты Lynis из шага 9, парольная политика из 9,
параметры Windows из 8в, уязвимости из 8/8а/8в, открытые сервисы из 7, слабые
учётки из 9а). Организационные меры помечены «проверяется вручную» и **не входят
в процент** — ни как выполненные, ни как проваленные. Мера, которую в прогоне
проверить не удалось (нет учётки, другая ОС), — «не проверена» и тоже не входит
в процент.

Как считается: мера на хосте **не выполнена**, если провалена хотя бы одна её
проверка; **выполнена** — если хотя бы одна проверка реально выполнялась и
нарушений нет. По группе/всем хостам мера не выполнена, если провалена хотя бы на
одном хосте. Процент = выполнено / (выполнено + не выполнено).

Нужен прогон шага 9а.11 (или 9 + 8в): соответствие считается автоматически в
конце прогона (`compliance_eval` в журнале аудита).

## Уборка после тестов

```bash
docker rm -f lab-web lab-ssh
rm -f lab_audit_key lab_audit_key.pub
docker network disconnect lab-net "$(docker compose ps -q app)"
docker network rm lab-net
```

Тестовый договор можно удалить под `admin`, учётные записи удаляются вместе
с ним. Прогоны и записи журнала аудита остаются в истории. Запомненные ключи
хостов стенда: `docker compose exec app sed -i '/^172\.30\.0\./d' /data/ssh_known_hosts`.
